# TestForge

## What this project is
A full-stack TestRail clone — test case management (projects, suites, sections, cases), test execution (runs, results, pass/fail history), planning (plans, milestones), reporting, a documented REST API, CSV import/export, and outbound webhooks. Built as both a portfolio piece (demonstrating full-stack engineering beyond QA automation, alongside the [parabank-playwright](https://github.com/jcpuatu/parabank-playwright) and [parabank-api-tests](https://github.com/jcpuatu/parabank-api-tests) portfolio projects) and an actually-usable internal test case management tool.

**Status: v1 complete, now mid-way through a systematic TestRail-parity expansion.** A user-led audit against ~20 of TestRail's own support-doc articles (support.testrail.com blocks WebFetch/403, so primary sources were pasted directly into the session rather than scraped) surfaced a long backlog of gaps — logged in full at `testrail_gap_audit.md` (session scratchpad) and turned into a phased implementation plan (Phase A–G) saved as a Claude Code plan file. Phases A–D are complete (see Roadmap below); Phase E (reporting/activity-log depth) is next. See Roadmap below for what's deliberately out of scope regardless of phase.

## Tech stack
- **Server:** Node + TypeScript + Express + Prisma (SQLite in dev, Postgres-portable) + Zod + Jest/Supertest + swagger-ui-express
- **Client:** React + TypeScript + Vite + Tailwind CSS v4 + TanStack Query + React Router
- **Monorepo:** npm workspaces (`server`, `client`)

## Data model — key decisions
- **SQLite has no native enum or Json type support** (validated the hard way — Prisma migration fails on both). All "enum-like" fields (`Role`, `Priority`, `CaseType`, `ResultStatus`, `WebhookEvent`) are `String` in the schema, validated at the API boundary via Zod and typed as literal unions in TS (`server/src/types/roles.ts`). Test-case `steps` are `String?` (JSON-serialized), converted to/from an array at the API boundary (`server/src/modules/cases/serialize.ts`, `runs/serialize.ts`).
- **`RunCase` snapshots case content** (title/steps/expected/priority) at run-creation time rather than just referencing `TestCase` — editing or deleting a case must not corrupt historical run results. `TestCase` uses a soft-delete flag (`isDeleted`) for the same reason.
- **`RunCase.status` is denormalized** for fast list queries; `Result` is append-only history (one row per status change/retest). Submitting a result (`POST /tests/:id/results`) updates both in one transaction (`server/src/modules/results/routes.ts`).
- **`Section`/`Milestone` self-relate via `parentId`** with `onDelete: Restrict` (not Cascade). Sections used to reparent children on delete; **changed to a real cascade delete** (subsections + their cases, hard-deleted) to match TestRail's actual documented behavior ("deleting a section will also delete any nested subsections and test cases... irreversible loss of test case data") — see `server/src/modules/sections/service.ts`'s `collectSectionSubtree` (BFS, then delete deepest-first so the Restrict constraint on the self-relation is never tripped) and the delete handler in `sections/routes.ts`. **Gotcha this uncovered:** deleting a *Suite* or *Project* relies on Prisma's declarative cascade through Section, which has no defined child-before-parent order — a suite/project containing a parent+child section pair (or nested milestones) threw a raw FK-constraint 500 until both delete handlers were fixed to `updateMany` all `parentId`s to `null` in scope *before* the cascading delete (`suites/routes.ts`, `projects/routes.ts`). Caught via live browser testing, not the test suite — if you add another self-relation like this, apply the same null-parents-first pattern before any cascade that spans it.
- **IDs are `cuid()` strings** everywhere — portable to Postgres, non-enumerable.
- **DATABASE_URL gotcha:** Prisma resolves relative SQLite paths against the directory containing `schema.prisma` (`server/prisma/`), not the process cwd. `DATABASE_URL="file:./dev.db"` in `server/.env` therefore resolves to `server/prisma/dev.db`. Using `file:./prisma/dev.db` doubles the path into `server/prisma/prisma/dev.db` — a mistake this project's history already made once.

## Auth design
- **Web app:** JWT access token (~15 min, returned in the login/refresh response body, kept in memory only on the client — never persisted) + an **opaque, rotating** refresh token in an httpOnly cookie (`server/src/modules/auth/service.ts`). Refresh tokens are stored only as a hash, rotated on every use, with **reuse-detection**: presenting an already-rotated token revokes the entire token family. No public self-registration — users are admin-provisioned (`POST /api/v1/users`, or the Users admin UI at `/admin/users`), matching real TestRail.
- **REST API:** API keys (`tf_` prefix, SHA-256 hash stored, raw key shown once at creation — self-service UI at `/account/api-keys`) sent as `Authorization: Bearer <key>`, handled by the same `requireAuth` middleware as JWT.
- **Client-side concurrency note:** the refresh call is deduped through a single in-flight promise (`client/src/lib/apiClient.ts` → `refreshSession()`), shared between the automatic 401-retry path and `AuthProvider`'s boot-time silent refresh. This was a real bug caught by browser testing — React StrictMode's double-effect-mount fired two concurrent `/auth/refresh` calls, and the second one tripped reuse-detection and could have revoked the session it had just created.
- **RBAC:** `requireRole(...roles)` middleware server-side; global `Role` (`ADMIN`/`LEAD`/`TESTER`/`VIEWER`) on `User`, not per-project. Roughly: ADMIN/LEAD manage structure (projects/suites/sections/runs/plans/milestones/webhooks/users), TESTER can additionally author cases and submit results, VIEWER is read-only. Client-side `ProtectedRoute` also accepts a `requireRole` prop for route-level gating (e.g. `/admin/users`), but the server is the actual enforcement point.

## Testing note — Prisma client + Jest
`server/src/config/prisma-client.ts` normally caches a `PrismaClient` singleton on `global` (for dev hot-reload). Under Jest, `global` persists across test files run in the same worker, which leaked one file's client (bound to its own isolated `DATABASE_URL`) into the next file's tests and caused "table does not exist" failures. Fixed by skipping the global-cache path when `process.env.JEST_WORKER_ID` is set — each test file gets its own fresh client. See `server/src/test/setup.ts` for how each file gets an isolated SQLite database.

## What's built
- **Auth & users** — login/refresh/logout, RBAC, admin-provisioned users, API keys (backend + admin UI)
- **Cases** — Project → Suite → Section (nested tree) → TestCase, full CRUD, CSV import/export. A **Filter + Sort bar** (`features/cases/CaseFilterBar.tsx`) sits above the case list — Section/Priority/Type/Created By checkboxes + a Created On date range, a Match-all(AND)/Match-any(OR) toggle for combining categories, and an independent Sort (field + direction) control that applies whether or not a filter is active. Whenever any filter criterion is set, the page switches from "one section's cases" to a suite-wide flat list (with a Section badge per row) via the already-existing-but-previously-unused `GET /suites/:suiteId/cases` endpoint, now extended with real query-building logic (`server/src/modules/cases/service.ts`'s `buildCaseListQuery`/`buildCaseSort`) instead of the three single-value params it had before.
- **Labels** — project-scoped tags on `TestCase` (`Label`/`TestCaseLabel` models, `server/src/modules/labels/`), positioned like real TestRail's own docs position them: a lighter-weight alternative to full custom fields, not a subset of them. Up to 10 per case, case-insensitive unique names per project (checked at the app layer — SQLite's default collation is case-sensitive), rename propagates automatically since every join row points at the same `Label.id`, delete cascades off every case that had it. Managed from an inline `LabelManager` reachable via "Manage labels" inside the case Filter dialog (`features/cases/CaseFilterBar.tsx`) rather than a separate admin screen — assignable from `CaseForm` (checkbox list, capped at 10) and usable as one more filter category. **Not yet built:** "Test" (RunCase)-level labels within a run — the audit found real TestRail supports both Case-level and separate Test-level labels; only the Case-level half is done.
- **Bulk case operations** (`features/cases/BulkCaseActionsBar.tsx`) — checkbox multi-select on the case list (same interaction pattern as the run-execution bulk-assign bar) drives bulk edit (priority/type/move-to-section — only the fields you actually set are changed, via `PATCH /cases/bulk-update`), bulk add-labels (additive, not replace-all — `POST /cases/bulk-add-labels`), and bulk delete (soft, `POST /cases/bulk-delete`). Selection auto-clears whenever the visible case list changes context (different section, filter toggled on/off, Show Deleted toggled) so a stale selection can never get bulk-edited invisibly. **Real routing bug caught here, worth remembering:** `PATCH /cases/bulk-update` had to be registered *before* the existing `PATCH /cases/:id` route — Express matches same-method routes in registration order, so `/:id` would otherwise greedily swallow `/bulk-update` as `id="bulk-update"`. Same class of issue as the FK-cascade bug below; check route registration order whenever a new `/bulk-*` or other literal-segment route is added alongside an existing `/:id` route on the same method.
- **Drag-and-drop** (`@dnd-kit/core` + `@dnd-kit/sortable`, `features/cases/SectionTree.tsx`) — real pointer-based drag (not native HTML5 DnD), covering: section reorder within a sibling group (each parent's children get their own `SortableContext`, so a drag can never cross into a different parent's group — reparenting isn't supported via drag, deliberately scoped out, see below), and dragging a case (via a dedicated grip handle, not the whole row, so it doesn't fight the row's click-to-expand/checkbox) onto a section in the sidebar to move it there — reuses the existing bulk-update endpoint, and moves the *entire* current multi-selection together if the dragged case is part of it. One shared `DndContext` at `SuiteDetailPage` level handles both concerns via an id-prefix convention (`case:<id>` vs a bare section id) since dnd-kit doesn't support nested `DndContext`s. **Deliberately out of scope for this pass** (documented, not silently dropped): reparenting a section via drag (only same-parent reorder is wired to the `/sections/:id/move` endpoint, which itself *does* support reparenting — the client just doesn't expose it yet), copy-via-Shift+drag (TestRail's modifier-key move/copy split), and cross-suite/cross-project drag targets (would need TestRail's own separate "Copy or Move" dialog, not a drag target). Projects, Suites, Plans, and Sections all support rename + delete from the UI (`components/ConfirmDialog.tsx` + a `GET .../delete-impact` preview endpoint on each, showing exactly what will be destroyed before confirming) — these existed as working, tested backend routes for a while with zero client wiring, found via a systematic audit and closed out together. Section/Suite/Project delete all hard-delete their contents (cases, and for Suite/Project, active runs too — closed runs are preserved), matching TestRail's own documented behavior rather than TestForge's earlier reparent-and-preserve shortcut. Test cases use soft-delete (`isDeleted`) with a "Show deleted" toggle, single + bulk restore, and a separate explicit "permanent delete" action only reachable after a case is already soft-deleted — mirrors TestRail's own two-tier delete model (no configurable retention window, unlike TestRail's 7/14/30-day admin setting — YAGNI at this scale).
- **Runs** — create (snapshot all-or-selected cases from a suite), execution UI (pass/fail/blocked/retest + comments/defects + per-test assignee picker), result history, close/reopen. Assignment mirrors TestRail's real assignment model (verified against TestRail support docs, not guessed) five ways: (1) per-row inline dropdown, (2) checkbox-select + "Assign selected" bulk bar, (3) a **"Filter by user"** panel (Select Me/All/None, Show Unassigned, per-user checkboxes, "Filter User" to apply) paired with **"Assign all in filter"** — filter the visible list down, then bulk-assign everything currently shown in one action, (4) an "Assign all tests to" picker on the run-creation form (both the standalone Test Runs page and the plan's "Add run to plan" form) that assigns every test in the run at creation, also reachable post-creation via `PATCH /runs/:id` with `assignedToId` (bulk-reassigns every `RunCase` in one step — distinct from the `TestRun` row itself, which has no such column), and (5) an inline "Assign to" picker inside the per-test result-submission form itself, defaulting to the test's current assignee — submitting a result now optionally reassigns in the same action instead of requiring a separate step first. All bulk paths go through real batched endpoints (`POST /runs/:id/tests/bulk-assign`, or a single `updateMany` inside the `PATCH /runs/:id` handler), not N individual requests.
- **My Tests** (`/my-tests`) — cross-project "assigned to me, in still-open runs" view, TestRail's dashboard to-do equivalent; `GET /users/directory` exposes a minimal (id/name/role) active-user list to any authenticated user so non-admins can populate assignee pickers
- **Plans & Milestones** — plans group runs, optionally tied to a milestone; milestones support due dates, completion, nesting
- **Rerun** (ADDS to, doesn't replace, the existing `Reopen` action) — a "Rerun" button on both `RunExecutionPage` and `PlanDetailPage`, opening a shared `RerunDialog.tsx`: a status checklist (defaults to Failed/Blocked/Retest, matching real TestRail's own default rerun selection) and a "Copy assigned to" checkbox. `runs/service.ts`'s `rerunRun` clones the ORIGINAL run's `RunCase` **snapshots** directly (title/steps/etc. exactly as they were), never re-pulling from the live `TestCase` — a rerun must test the exact instructions that produced the selected statuses, not a possibly-since-edited version, consistent with the project's existing run-immutability discipline. "Rerun plan" (`plans/service.ts`'s `rerunPlan`) reruns every run in the plan independently with the same filter and attaches the new runs back onto the same plan — simpler than spinning up a whole new plan (deliberate scope reduction); a run with nothing matching the selected statuses is skipped rather than failing the whole batch, and the client reports how many were skipped. `Reopen` remains as a documented, deliberate non-standard escape hatch (real TestRail treats closed runs as permanent); Rerun is the correct/primary "continue after closing" workflow.
- **Configurations** — project-scoped `ConfigGroup` (e.g. "Browsers") containing named `Config` values (e.g. "Chrome"), managed via `ConfigurationsManager.tsx` (reached from a "Manage configurations" link inside the plan's "Add run to plan" form, matching real TestRail's own entry point — not a separate settings page). Selecting one or more config values in that form and submitting calls `POST /plans/:planId/runs/by-config` (`runs/service.ts`'s `createRunsForConfigs`) instead of the normal single-run endpoint, creating **one run per selected config** (each named `"<name> (<config>)"`, tagged via the previously-unused `configLabel` free-text field as `"<group>: <config>"`). Deliberately simpler than real TestRail's full cross-group combination matrix — selecting configs from multiple different groups still yields one run per config, not a cartesian product across groups (e.g. picking one browser + one OS makes 2 runs, not 1 run tagged with both). `configLabel` is a plain string snapshot, not a live link to the `Config` row, so deleting a config group later doesn't affect runs already created from it.
- **Milestone Upcoming/Open/Completed lifecycle** — purely derived client-side (`computeStatus` in `MilestonesTab.tsx`), not a stored field: no `startDate` or `startDate` already in the past → Open; a future `startDate` → Upcoming; `isCompleted` → Completed (checked first, takes priority). "Start milestone" (shown only while Upcoming) backdates `startDate` to now via the existing `PATCH` endpoint — no new server route needed. The tab also now renders the existing `parentId` self-relation as a real indented tree (same `buildTree`-by-`parentId` + depth-based `marginLeft` shape as `SuiteDetailPage`'s section indentation) with a parent picker on the create form; reassigning a milestone's parent after creation isn't exposed (deliberate scope reduction, same precedent as Section's drag-reorder-only-no-reparent-via-edit).
- **Date inheritance (Milestone → Plan → Run)** — `Milestone.startDate`/`dueDate`, `TestPlan.startDate`/`endDate`, `TestRun.startDate`/`endDate` are each independently nullable; a null value means "inherits from parent" and is resolved at **display time**, not copied down at creation — the client computes and shows "Inherits plan end date: X" (or milestone due date, one level further up) whenever a Plan/Run has no explicit date of its own. Editable only while the entity isn't completed (both client-hidden and server-enforced — a `PATCH` with a date field on an already-completed Milestone/Plan/Run returns 400). A non-blocking amber warning banner appears if a Plan's/Run's own end date is later than its parent's, but nothing prevents saving it. `Milestone.references` and `TestPlan.referenceId` are both free-text external-ticket-link fields, matching `TestCase.referenceLink`'s existing convention.
- **Reporting** — project dashboard (stat tiles + per-run stacked status bars, palette validated via the dataviz skill's contrast/CVD checker)
- **REST API** — versioned `/api/v1`, documented via OpenAPI/Swagger UI, dual auth (JWT or API key)
- **Webhooks** — outbound HMAC-signed POST on `RUN_CREATED`/`RUN_COMPLETED`/`CASE_CREATED`, delivery log, test-ping button
- **Defect linking (Jira stand-in, not a real integration)** — `Result.defects` is free text (comma-separated IDs/URLs), rendered as a clickable link when it looks like a URL (`client/src/components/DefectText.tsx`); a red bug icon appears on a test row when its latest result is Failed/Blocked with a defect attached; the Defect IDs input autocompletes from defect IDs already used elsewhere in the project. A **Defects tab** (`GET /projects/:id/defects`) rolls up every defect ID across the project — reference count, how many cases are still failing vs. look resolved, last-seen date. A **"Draft defect for Jira"** panel on each test auto-generates a title/description (steps, expected/actual, environment, reporter, deep link back to TestForge) with a copy-to-clipboard button, plus an optional locally-saved Jira "create issue" URL for one-click prefill (real Jira feature, no API key needed, best-effort on newer Jira Cloud UIs). A run's **"Export defects CSV"** button bulk-exports every Failed/Blocked test as a Jira-bulk-import-shaped CSV (Summary/Description/Issue Type/Priority/Labels) — reuses the same `lib/csv.ts` encoder as case import/export. None of this talks to a real Jira instance — a genuine push-to-Jira integration (create + live status sync) would need real Jira credentials to build and test against, which isn't available; this is the deliberate middle ground that needed none.
- **Case templates** — `TestCase.template` (`TEXT`/`STEPS`/`EXPLORATORY`/`BDD`, default `TEXT`) switches which fields `CaseForm.tsx` renders: TEXT is a single freeform Steps paragraph (stored as a one-entry `steps` array, no per-step `expected`) alongside Preconditions/Overall-expected-result; STEPS is the original per-line `"step | expected"` format; EXPLORATORY swaps Preconditions/Steps/Expected for Mission/Goals fields. BDD is defined in the schema/enum but deliberately not yet selectable in the UI — it gets its own Gherkin scenario editor instead of these fields, not built yet. `RunCase` snapshots `templateSnapshot`/`missionSnapshot`/`goalsSnapshot` alongside the existing title/steps/expected snapshots, so `RunExecutionPage` renders the right shape (steps list, single paragraph, or mission/goals) per test independent of later edits to the source case. **Migration gotcha worth remembering:** the `template` column's SQL default (`'TEXT'`) would have mislabeled every pre-existing case/run-case (all authored under the old always-STEPS-shaped form) — the migration includes an explicit backfill (`UPDATE ... SET template = 'STEPS'` for rows that existed before it) rather than relying on the column default, and the same backfill was run once directly against the live dev database (not via `migrate reset`, which would have wiped real project data) since Prisma migrations only run automatically on new/pending migrations, not retroactively on data already covered by an already-applied one.
- **Shared Steps** — project-scoped, named, reusable step lists (`SharedStepSet` + a `TestCaseSharedSteps` join, `server/src/modules/sharedSteps/`). A STEPS-template case can attach any number of sets (checkbox list in `CaseForm`), rendered as their own "Shared: <name>" block after the case's own literal steps, or created directly from a case's current steps via "Promote these steps to a reusable shared step set". Live-linked at the case level — a set's content is always resolved at read time (`toPublicCase`'s `sharedSteps` field), so editing a set immediately updates every case using it. Runs are the one place this does NOT apply: `resolveStepsForCases` (`server/src/modules/sharedSteps/service.ts`) flattens each case's own steps + every attached set's steps into one array once at run-creation time, matching the existing run-immutability invariant — a shared set edited (or deleted) after a run was created never alters that run's history. Reachable via a "Shared Steps" link on the Test Cases page (`SharedStepsManager.tsx`, opened in a `Modal`). Scope reduction from real TestRail, documented not silently dropped: sets always append after a case's own steps (no interleaving at an arbitrary position), and "promote" always takes ALL of a case's current steps (TestRail supports promoting an arbitrary consecutive range); version history for a set's past content is not built.
- **BDD Scenario template** — a fourth `TestCase.template` value; `bddLines` (JSON array of `{keyword: Given/When/Then/And/But, text}`) replaces Preconditions/Steps/Expected entirely (mirrors how Exploratory replaces them with Mission/Goals). `RunCase.bddLinesSnapshot` follows the same immutable-snapshot rule as every other template's content. A hand-rolled Gherkin subset parser/formatter (`server/src/modules/cases/gherkin.ts`, no external Cucumber dependency) powers **`.feature` file export/import** (`GET/POST /suites/:suiteId/cases/export-feature` and `/import-feature`, buttons next to the existing CSV ones on the Test Cases page) — export bundles every BDD-template case in a suite as one file (`Feature: <suite name>`, one `Scenario:` block per case); import auto-creates (or reuses, by name) a section named after the file's `Feature:` line, matching the CSV importer's by-name section convention, then creates one BDD-template case per `Scenario:` block. Deliberately-scoped-down vs. real Cucumber/TestRail, documented not silently dropped: `Background:` steps, `Examples:` tables (Scenario Outline data rows), and `@tags` are recognized during parsing (so they don't break import) but not stored or round-tripped.
- **Per-step results** — `Result.stepResults` (JSON array of `{status, actual}`, positionally matching `RunCase.stepsSnapshot`) lets a STEPS-template test record a status + optional actual-result text per step, not just one overall status. The per-step controls render inline in the execution UI only when submitting (read-only viewers still see the plain numbered step list); the existing overall PASSED/FAILED/BLOCKED/RETEST buttons remain the single required submit action — TestForge does not auto-derive the overall status from per-step statuses (a real but undocumented-in-the-audit-material TestRail behavior; left as a manual choice to avoid guessing at an unspecified algorithm). Result history shows each past submission's per-step breakdown when present.
- **Activity log** — `AuditLog` model, written to from a deliberately small, specific list of actions (not a generic log-everything hook): label rename/delete, section/suite/case delete, milestone/plan/run date changes, run close. `lib/audit.ts`'s `logAudit` is called directly from each route handler after the mutation succeeds. A project-scoped chronological feed (`features/activity/ActivityTab.tsx`, reachable via a new "Activity" sidebar tab) shows the actor, a human-readable summary, and timestamp for the last 200 entries.
- **Light/dark theme toggle** — see Theme system below.
- **Shared UI infra added for the TestRail-parity work** — `components/Modal.tsx` (hand-rolled overlay/panel, Esc-to-close, click-outside-to-close), `components/ConfirmDialog.tsx` (built on Modal, used for every destructive action), `components/Toast.tsx` + `ToastProvider`/`useToast()` (bottom-right stacked success/error toasts, 4s auto-dismiss) — mounted once in `App.tsx` alongside `ThemeProvider`. Existing per-page inline `formError` state is kept for form-validation errors; Toast is specifically for action-result feedback (delete/restore/rename outcomes, bulk operations).

## Theme system
- `client/src/features/theme/ThemeContext.tsx` — `ThemeProvider`/`useTheme()`; persists to `localStorage` (`testforge:theme`), defaults to the OS `prefers-color-scheme` on first visit, and toggles a `dark` class on `<html>`. Tailwind v4's class-based dark mode is enabled via `@custom-variant dark (&:where(.dark, .dark *));` in `client/src/index.css` (no `tailwind.config.js` needed).
- Toggle button lives in `AppShell`'s header (`client/src/layouts/AppShell.tsx`), sun/moon icon from `lucide-react`.
- Every page/component carries `dark:` variants on its color utilities (text/bg/border). Convention: card surfaces `bg-white` → `dark:bg-slate-800`, inset sections (e.g. comment boxes, bulk-action bars) `bg-slate-50` → `dark:bg-slate-700`, borders one step darker (`border-slate-200` → `dark:border-slate-700`), status/priority pill backgrounds use Tailwind's opacity-modifier shorthand (`dark:bg-emerald-900/50`) rather than a flat dark shade, to keep them visibly tinted without glowing on a dark page.
- **Bulk dark-variant rollout bug (worth knowing before scripting a similar pass again):** the first attempt applied ~14 regex substitution rules sequentially, each re-scanning the output of the previous rule — since some rules are near-inverses of each other (e.g. `text-slate-500`→`dark:text-slate-400` and `text-slate-400`→`dark:text-slate-500`), later rules matched dark-variant classes just inserted by earlier rules and appended a second, wrong suffix (`dark:text-slate-400 dark:text-slate-500` stacked on one class). Fixed by rewriting it as a single lookup-table pass — one combined regex alternation over all light-mode tokens, matched once against the pristine original file content with a replacement function — so no rule ever sees another rule's output. If a similar bulk rewrite is needed later, do it as one non-overlapping pass, not N sequential passes over shared state.
- **`bg-slate-50` needed manual disambiguation**, not a blanket rule — it plays three different visual roles in this codebase (page-wrapper background on `LoginPage` → `dark:bg-slate-900`; an inset section inside a card, e.g. `RunExecutionPage`'s comment box/bulk-action bar → `dark:bg-slate-700`; a row hover state on `MyTestsPage` → `dark:hover:bg-slate-800`). A single global mapping would have made the login page's outer background and its white card visually identical in dark mode.
- **Found via this pass, unrelated to dark mode itself:** `components/Badge.tsx`'s generic `Badge` component applied its own default `bg-slate-100`/`text-slate-600` classes unconditionally, then appended the caller's override `className` after them via `clsx`. Same-specificity Tailwind utilities are resolved by generated-CSS order, not class-attribute order, so the default sometimes won over the override (e.g. `RunsListPage`'s "Active" run badge rendered gray instead of emerald, in light mode too, before this fix). Fixed by only applying the default color classes when the caller's `className` doesn't itself contain a `bg-` token.
