# TestForge — client

See the root `CLAUDE.md` for overall project context and auth design. This file covers client-specific conventions.

## Conventions
- **Tailwind v4** — no `tailwind.config.js`/`postcss.config.js`; styling is wired via the `@tailwindcss/vite` plugin in `vite.config.ts` and a single `@import "tailwindcss";` in `src/index.css`. Don't reintroduce the v3-style config files, they're not needed and won't be picked up.
- **No shadcn/ui CLI generation** — `src/components/{Button,Input,Badge,StackedStatusBar,Modal,ConfirmDialog,Toast}.tsx` are small hand-rolled Tailwind-styled primitives instead. Extend these rather than pulling in a component library, unless the UI needs grow substantially (then reconsider shadcn's actual CLI, which requires an interactive `init` step).
- **Drag-and-drop** uses `@dnd-kit/core`/`@dnd-kit/sortable` — real pointer-based DnD, not native HTML5 drag events (matters for Playwright verification scripts too: use manual `mouse.move`/`down`/`up` sequences with a few intermediate steps, not `page.dragTo()`, to trigger dnd-kit's `PointerSensor` distance-activation threshold). One shared `DndContext` lives at `SuiteDetailPage` level (dnd-kit doesn't support nesting contexts), and `features/cases/SectionTree.tsx` is a purely presentational component that calls `useSortable`/`useDroppable` internally — it works because it's rendered as a descendant of that one `DndContext`, not because it owns one itself. Drag sources use an id-prefix convention (`case:<id>` for cases, a bare section id for sections) so `SuiteDetailPage`'s single `handleDragEnd` can route to the right mutation. A case row's drag affordance is a dedicated `GripVertical` handle component (`CaseDragHandle`), not the whole row — `useDraggable` can't be called conditionally inside the row's `.map()`, so it has to live in its own tiny component, and a full-row-draggable would fight the row's own click-to-expand/checkbox interactions anyway.
- **`SectionTree.tsx` renders the section tree recursively, not via flatten-then-group-by-parent** — a real user-reported bug (reproduced with everything expanded, not just a collapse-state issue): the original render grouped every node into one `Map<parentId, ids[]>` and rendered each group as its own block in `Map` insertion order. Since the depth-first tree walk visits every top-level parent before descending into any of their children, insertion order came out as `[null → all top-level rows]` then `[ParentA.id → its children]` then `[ParentB.id → its children]` — so with 2+ parent sections that each have children, the DOM order became "every parent row, then Parent A's children, then Parent B's children" instead of the correct nested order. Fixed by rendering recursively: each parent's own `SortableContext` (scoped to just its direct children, dnd-kit's normal nested-sortable-list pattern) renders immediately after that parent's row, and collapse just skips recursing into a node's children rather than filtering a separately-flattened list. If you build another nested-tree UI, render recursively from the start — flattening to a grouped `Map` and rendering group-by-group silently breaks interleaving as soon as there's more than one branch.
- **Bulk case operations** (`features/cases/BulkCaseActionsBar.tsx`) reuse the checkbox-`Set<string>`-selection pattern from `RunExecutionPage.tsx`'s bulk-assign bar. `SuiteDetailPage.tsx` clears the selection via a `useEffect` keyed on `[activeSectionId, filtering, showDeleted]` — any of those changing means the visible case list changed, so a stale selection must not silently carry over into the next bulk action.
- **Labels** — project-scoped tags on cases, managed inline via `features/cases/LabelManager.tsx` (rendered inside `CaseFilterBar`'s Filter dialog behind a "Manage labels" toggle, not a separate settings page). `CaseForm` takes an `availableLabels` prop and renders a capped-at-10 checkbox list; `TestCase.labels` is always the full label objects (not just ids) so rows can render pills directly without an extra lookup.
- **Case templates** (`features/cases/CaseForm.tsx`) — a `template` select (`TEXT`/`STEPS`/`EXPLORATORY`; `BDD` is a valid enum value but deliberately not offered here yet, pending its own scenario editor) switches which fields render below it. TEXT and STEPS both use `TestCase.steps`, but with different in-memory state (`textSteps` plain string vs. `stepsText` pipe-delimited-per-line) so switching templates in the form can't garble one format into the other — keep this split if you touch the form's local state.
- **Reports** (`features/reports/`) — `ReportsPage.tsx` tracks the active report via a `?report=` search param (not a nested route per report), so adding a new report type is just another entry in its `CATEGORIES` array. Each report page composes small shared pieces directly (`SectionCheckboxList`, `RunCheckboxList`, `DateRangePresetPicker`, wrapped in a `ReportShell` layout) rather than going through one generic config-driven filter-dialog abstraction — the four Cases Reports' filter shapes differ enough (date-range+groupBy vs. reference-mode vs. run-selection) that a single abstraction would have added more complexity than it saved; reuse these small pieces directly for new reports, don't build a bigger shared dialog around them. **`components/ActivityOverTimeChart.tsx`'s per-period column div needs an explicit `style={{ height: '100%' }}`, not just its parent's `items-end` flex alignment** — `items-end` overrides flexbox's default `stretch` behavior, so without the explicit height the column div sizes to `auto` (shrink-to-fit), and the bar children's `height: X%` styles then resolve against an indeterminate parent height and collapse to near-zero (confirmed via a browser screenshot showing flat 2px lines instead of bars, before this fix). Any future bar-chart-via-percentage-height built inside a flex container needs the same explicit stretch — don't assume `items-end` alone gives children a definite height to size against.
- **`components/Modal.tsx` is bounded to `max-h-[85vh]` with the content area (not the header/footer) as the only scrolling region** — the panel is a flex column, header and footer both carry `shrink-0`, and only the middle `overflow-y-auto` div grows/scrolls. Found via a real user bug report: `CaseHistoryModal` with 8+ runs had no way to reach content that overflowed the viewport before this fix. An optional `size?: 'md'|'lg'|'xl'` prop (default `md`, i.e. the original `max-w-md`) lets content-heavy modals opt into more width — `CaseHistoryModal` is the first `size="lg"` user. Every other `<Modal>` caller is unaffected (same default width, and none of them are tall enough to trigger the new scroll behavior in normal use).
- **Row layout with unbounded-length content (e.g. a pasted defect URL) needs its own line, not a shared `justify-between` row with a fixed-content sibling** — `CaseHistoryModal`'s Runs list originally put the run name and the defect+status on one `flex justify-between` line; a long defect URL had no `min-w-0`/`truncate` anywhere in that row, so it could push the row wider than the modal and visually collide with the status badge. Fixed by giving the defect its own line below the run name (both independently `truncate`d with a `title` attribute for the full value on hover), and applying the same `min-w-0 flex-1 truncate` + `shrink-0` split to the sibling "Defects" rollup section, which had the identical risk. If you add another row that mixes a free-text/URL-shaped field with fixed-width siblings, default to stacking rather than a single `justify-between` line — it's the only guarantee-safe layout that doesn't depend on knowing the field's max length ahead of time.
- **Print (Phase K)** — `components/PrintButton.tsx` (`window.print()`) pairs with `@media print` rules in `index.css` that hide `header`/`aside` globally and any element carrying a `.no-print` class. `header`/`aside` are used consistently for AppShell's top bar and every sidebar (ProjectShell's project nav, `SuiteDetailPage`'s section tree), so hiding them by bare tag is safe project-wide — don't rename either of those to a `<div>` without checking this. Any page-specific chrome (a filter bar, a bulk-action row, an "Edit dates" toggle) needs its own explicit `.no-print` class since it isn't inside either container.
- **CSV export (Phase K)** — `lib/downloadCsv.ts`'s `downloadTableAsCsv(headers, rows, filename)` generates and downloads a CSV entirely client-side (the report's data is already loaded via its own `useQuery`, so there's no reason to round-trip to the server the way `api/csv.ts`'s case-export does). `components/DownloadCsvButton.tsx` is the shared button. `MatrixTable`, `PropertyDistributionChart`, and `SummaryReportView` each take an opt-in `csvFilename` prop — pass one to get a working Download CSV button for free; omit it for a chart/table-only usage. A report whose table shape doesn't fit any of those three shared components wires `downloadTableAsCsv` directly instead (see `ActivitySummaryReport.tsx`, `CoverageForReferencesReport.tsx`, `StatusTopsReport.tsx`, `DefectsSummaryReport.tsx` for the pattern).
- **`features/reports/summary/SummaryReportView.tsx`** is the one shared body for all four Summary reports (Milestone/Plan/Project/Runs) — Status/Activity/Progress/Runs/Tests sections, purely presentational over whatever `SummaryReportData` the caller's page already fetched. Each of the 4 page wrappers only differs in how it resolves scope: Milestone/Plan render a `Select` picker (defaulting to the first item in the list) before rendering the shared view, Project needs no picker at all, Runs reuses `RunCheckboxList` with an explicit "none selected = empty report" label since — unlike every other run-scoped report in this app — Runs Summary does NOT default to "25 most recent" when nothing is checked. Add a 5th Summary-shaped report the same way: a thin wrapper that resolves its own scope and renders `<SummaryReportView data={...} csvFilename="..." />`, not a new copy of the Status/Activity/Progress markup. It's also the one place `StackedStatusBar`'s `onSegmentClick` is wired up (Phase K) — clicking a status segment or legend entry filters the Tests list to that status via local `statusFilter` state; the CSV download and the "filtered to X — clear" label both read from the same filtered list, not the raw `data.tests`.
- **`features/reports/MatrixTable.tsx`** renders the cases×runs grid shared by 4 Defects/Results reports (Summary for Cases/References, Comparison for Cases/References) — one `<table>`, columns driven by whatever `runs` array the caller passes, an optional `showDefects` prop to render defect-ID chips under a cell's status badge. Reused directly (not wrapped again) by each report page; don't build a second matrix-rendering component for a future report with the same case×run shape.
- **CSV export picker** (`features/cases/CsvExportDialog.tsx`) reuses `SuiteDetailPage`'s already-computed indented `sections` list (the same `depth`-based rendering `SectionTree`/the parent-picker dropdowns use elsewhere) for its section checkboxes, so the picker's tree shape always matches the sidebar's. Leaving all sections unchecked exports everything (not "export nothing") — the empty-selection case is treated as "no filter," matching the same convention `CaseFilterBar`'s category checkboxes already use. `api/csv.ts`'s `downloadCasesCsv` takes an optional `{ sectionIds, columns }` and appends them as query params before the existing fetch-blob-trigger-click download flow — reuse that function's signature rather than adding a second export helper.
- **Attachments** — `components/AttachmentsPanel.tsx` is a shared presentational component using native HTML5 `dragover`/`drop` events, not `@dnd-kit` — this is an OS-file-drop zone, a deliberately different tool from `@dnd-kit`'s in-app element-reordering used elsewhere in this codebase. `features/cases/CaseAttachments.tsx` and `features/runs/ResultAttachments.tsx` are thin `useQuery`/`useMutation` wrappers around it, scoped to a case or a result respectively; `ResultAttachments` renders `null` when read-only and empty, so historical result rows a viewer can't edit don't show a bare empty panel. FormData uploads can't go through the shared JSON-only `apiFetch`, so `api/attachments.ts`'s `uploadFile` is a separate raw-`fetch` helper that still preserves `apiFetch`'s one-retry-after-token-refresh behavior — reuse it (not `apiFetch`) for any future multipart upload.
- **Keyboard shortcuts + Pass & Next** (`RunExecutionPage.tsx`) — the "currently expanded test" is lifted to `activeTestId` state on the page itself (not local `useState` inside each `TestRow`, which the earlier one-test-at-a-time design used) specifically so a page-level "what's active" concept exists for shortcuts and advancing to work against. `P`/`F`/`B`/`R` set a result on whichever row is expanded, ignored while a text field has focus; only `P` ("Pass & Next") auto-advances to the next `UNTESTED` test and scrolls it into view — `F`/`B`/`R` don't, since a failure usually needs a comment/defect added before moving on. `submitStatus(status, advance?)` is the one call site both the keyboard handler and the on-screen buttons go through, so behavior can't drift between the two input paths.
- **Per-step *result entry* was removed from the execution screen (kept the *display*)** — real user feedback: a tester importing a large real-world CSV (STEPS-template cases, correctly showing all their steps per the BOM/template-defaulting fixes above) disliked the per-step Pass/Fail/Blocked/Retest dropdown + "Actual result" input rendered next to every step during submission. The fix removes only the editable controls (and the `stepStatuses`/`stepActuals` local state, and the `stepResults` field from the submit payload) — a STEPS-template case's numbered step list (with `step → expected`) still always renders read-only during execution, same as before, so no step content becomes less visible. `Result.stepResults` still exists in the schema and `RunExecutionPage`'s History view still renders a past submission's per-step breakdown if one exists (from data recorded before this change, or via the API directly) — this only removes the *input* path, not the *data model* or historical *display*, so no existing data is hidden or lost. If per-step result entry is ever wanted back, it was a small, self-contained UI feature (see git history around this point) — don't rebuild the data model, just the input controls.
- **Shared Steps** (`features/cases/SharedStepsManager.tsx`, opened from a "Shared Steps" link on the Test Cases page toolbar via `Modal`, not nested in the Filter dialog like Labels — there's no "filter by shared step set" concept) — `CaseForm`'s STEPS-template branch exposes a checkbox list (`availableSharedStepSets` prop) to attach sets, plus an inline "Promote these steps…" action that calls the promote endpoint directly via its own `useMutation` (a side-action outside the form's normal `onSubmit`-assembles-`CaseInput` flow, so it can't reuse that path) and invalidates via a `predicate` matching any query key containing `'cases'` or `'shared-step-sets'` — necessary because case lists live under two different key prefixes (`['sections', ...]` and `['suites', ...]`), not one.
- **Case filtering/sorting** (`features/cases/CaseFilterBar.tsx`) reuses `PRIORITIES`/`TYPES` exported from `CaseForm.tsx` rather than redefining them — keep those two in sync if the enums ever change. The filter bar's presence flips `SuiteDetailPage` between two different case-list queries (`listCasesBySection` vs. suite-wide `listCasesBySuite`); see `isFilterActive()` in `api/cases.ts` for the switch condition.
- **Destructive actions go through `ConfirmDialog`** (built on `Modal`), not a bare click-to-delete. For deletes with real blast radius (suite/section/project), fetch the paired `GET .../delete-impact` endpoint and show the actual counts in the dialog body before the user confirms — see `SuiteDetailPage.tsx` for the pattern (suite delete, section delete, and case restore all follow it). `useToast()` (from `components/Toast.tsx`, provider mounted in `App.tsx`) reports the outcome after the mutation settles; keep using local `formError` state for in-form validation errors, Toast is for action results.
- **Access token is memory-only** (`src/lib/tokenStore.ts`) — never persisted to storage, to limit XSS blast radius. Session survival across reloads relies entirely on the httpOnly refresh cookie via a silent `/auth/refresh` call in `AuthProvider`'s boot effect (`src/features/auth/AuthContext.tsx`).
- **Refresh calls are deduplicated** through `refreshSession()` in `src/lib/apiClient.ts` — a single in-flight promise shared by the automatic 401-retry path and `AuthProvider`'s boot-time refresh. Do not call `POST /auth/refresh` directly from anywhere else; go through `refreshSession()`/`api/auth.ts`'s `refresh()`, or you'll reintroduce the concurrent-refresh race that was caught during browser verification (see root `CLAUDE.md`).
- **API layer:** `src/api/<resource>.ts` are thin typed wrappers around `apiFetch` (`src/lib/apiClient.ts`); pages call these directly through TanStack Query's `useQuery`/`useMutation` rather than through a separate hooks layer.
- **Steps editor is a line-based textarea**, not a repeatable-row form (`src/features/cases/stepsText.ts`: `"step | expected result"` per line). This mirrors the server's CSV round-trip format (`server/src/modules/cases/stepsFormat.ts`) — keep them in sync if either changes.
- **Project pages are nested routes under `ProjectShell`** (`src/features/projects/ProjectShell.tsx`), which fetches the project once and renders it as a left sidebar nav (icons via `lucide-react`) + `Outlet` context — tab pages read `{ project }` via `useOutletContext`. Sidebar items: Overview (`ReportsTab`), Test Cases, Test Runs & Results, Test Plans, Milestones, and Webhooks (ADMIN/LEAD only, conditionally appended). This structure — dark top header (`#1F2D35`) + light sidebar with icon nav + light-blue active-state highlight — deliberately mirrors real TestRail's actual UI (verified against TestRail 9.0 product screenshots, not guessed), not just its feature set. If you add a new project-scoped section, add it to `ProjectShell`'s `TABS`/`ADMIN_TABS` array with a `lucide-react` icon, not as a separate top-level route.
- **Status color convention** (used in `StatusBadge`/`StackedStatusBar`/`PriorityBadge` in `components/Badge.tsx` and `components/StackedStatusBar.tsx`): PASSED=emerald, FAILED=red, BLOCKED=orange, RETEST=cyan, UNTESTED=slate. RETEST was originally purple; switched to cyan after cross-checking real TestRail screenshots, since that's what TestRail itself uses. This palette went through the `dataviz` skill's validator; reuse `StackedStatusBar`/`StatusLegend` for any new chart involving result statuses rather than re-deriving colors.
- **Primary accent is `blue`, not `indigo`** (Tailwind's `blue-*` scale) — matches TestRail's actual link/button blue more closely than indigo does. Don't reintroduce indigo classes.
- **CSV export downloads via blob**, not a plain `<a href>` — the export endpoint requires an `Authorization` header, which a bare link navigation can't attach. See `downloadCasesCsv` in `src/api/csv.ts` for the fetch-blob-trigger-click pattern; reuse it if another authenticated download is added.
- **Admin routes** (`/admin/users`) are gated via `ProtectedRoute`'s optional `requireRole` prop (`src/routes/ProtectedRoute.tsx`) in addition to the server enforcing RBAC — the client check is UX only, never the security boundary.
- **Defect linking is client-heavy** since the server has no `Defect` entity: `components/DefectText.tsx` linkifies a defect string when it looks like a URL; the Defect IDs `<input>` on a test row pairs with a `<datalist>` populated from `GET /projects/:id/defects` for autocomplete; `features/runs/DraftDefectPanel.tsx` generates a Jira-ready title/description purely from data already on the page (case steps/expected, the in-progress comment, run/suite name) — no new fetch needed. The optional "Jira create-issue URL" for one-click prefill is saved to `localStorage` (key `testforge:jiraCreateUrl`), not the backend — it's a personal browser setting, not a project setting, by design (no schema for it exists).
- **Light/dark theme** — `features/theme/ThemeContext.tsx` (`ThemeProvider`/`useTheme()`) toggles a `dark` class on `<html>` and persists to `localStorage` (`testforge:theme`); Tailwind's class-based dark mode is enabled via `@custom-variant dark (&:where(.dark, .dark *));` in `index.css`. When adding new UI, pair every color utility with a `dark:` variant — see root `CLAUDE.md`'s Theme system section for the color-mapping convention and two bugs worth knowing about (a cascading-regex bulk-rollout bug, and a `Badge` component default-vs-override class collision) before touching this again.
- **`components/Badge.tsx`'s generic `Badge`** only applies its own default gray color classes when the caller's `className` doesn't itself contain a `bg-` token — pass a full `bg-*`/`text-*` pair (both light and `dark:` variants) to override the color, not just one of the two, or you'll get a partial mix of default and override colors.
- **A shorthand `border-{color}` and a directional `border-l-{color}` both ultimately set `border-left-color` once Tailwind expands them, so combining them is the same cascade-order hazard as the `Select`/`Badge` bugs below** — `RunExecutionPage.tsx`'s `TestRow` needed a status-colored left accent bar (`border-l-4` + a per-status color) alongside its existing bottom divider; writing `border-b border-slate-200 border-l-emerald-500` would make which color wins for the left edge depend on Tailwind's generated-CSS order, not source order. Fixed by using `border-b-slate-200`/`dark:border-b-slate-700` (bottom-only) instead of the `border-slate-200` shorthand, so the bottom-color and left-color utilities target entirely different longhand properties and can never collide. Reuse this pattern (directional-only utilities, never a shorthand alongside a directional override of the same property) any time a component needs different colors/widths on different sides.
- **Execution-flow visual hierarchy** (`RunExecutionPage.tsx`'s expanded `TestRow`) — the Pass & Next/Failed/Blocked/Retest buttons are separated from the Comment/Defect/Version/Elapsed/Assign fields above them by a `border-t` divider and are a size step larger (`py-2 text-sm` vs. the fields' implicit smaller sizing) specifically because they're clicked far more often than any single field and deserve more visual weight — but they're deliberately **not** reordered above those fields, since recording why a test failed before committing the status is the more correct QA workflow, not just a smaller-scroll-distance one. If you touch this area again, preserve that field-then-action ordering rather than "optimizing" it away.
- **"Pass & Next" quick-advance dropdown** — confirmed against TestRail's own "Submitting test results" support doc (pasted directly, not assumed): the real Pass & Next button has an attached arrow that lets you quick-submit *any* status (not just Passed) through the same auto-advancing path. TestForge's original Phase F implementation only advanced on Passed — a plausible-sounding but unverified assumption made before this doc existed ("a failure usually needs a comment/defect first"), not something checked against the real product. Closed the gap by adding a chevron button next to Pass & Next (`showQuickAdvanceMenu` state) opening a small menu of `${status} & Next` options that call the same `submitStatus(status, true)` path — this is *additive*, not a replacement: the plain Failed/Blocked/Retest buttons beside it still submit without advancing, for a tester who deliberately wants to stay and add detail first. Both paths coexist because both are real, valid workflows. **The menu didn't close on an outside click** (only re-clicking the chevron itself closed it) — fixed with a `quickAdvanceRef` on the menu's wrapping `<div>` plus a document-level `mousedown` listener in a `useEffect` that closes the menu when the click target falls outside that ref. This is a plain manual listener, not a library (no click-outside dependency exists in this codebase) — reuse the same ref+`mousedown`-listener shape for any future dropdown/popover that needs the same behavior.
- **A running per-test elapsed timer used to be lost on navigation, and (more severely) on submit-without-stopping** (`RunExecutionPage.tsx`) — the timer's start timestamp lived only in React state, so switching runs/tabs mid-timer and coming back reset it to zero. Fixed by writing the start timestamp to `sessionStorage` under a per-test key (`` `testforge:timer:${test.id}` ``) on start/stop, and seeding the `timerStartedAt` state's `useState` initializer by reading that key back — a remount (from navigation, or a re-render) now resumes the same live timer instead of losing it. The more severe sibling bug this surfaced: submitting a result *without* first clicking Stop read the frozen, pre-timer `elapsedSeconds` string instead of the actual live value, silently discarding however long the timer had really been running. `submitResult`'s mutation now computes elapsed from `Date.now() - timerStartedAt` whenever a timer is still live at submit time, falling back to the frozen value only when no timer was ever started.
- **"This test run is completed" banner** (`RunExecutionPage.tsx`, right below the header, `run.isCompleted` gated) — confirmed against TestRail's "Closing test runs and plans" doc; previously `isCompleted` only affected button visibility/disabling with no prominent on-page indicator. That same doc also confirms TestForge's `Reopen` feature is a deliberate, documented *deviation* from real TestRail, not an oversight — real TestRail explicitly does not allow reopening a closed run ("closing a test run cannot be undone"); rerun is the only real path back, which TestForge also has. Don't "fix" Reopen to match TestRail by removing it — that was already an intentional non-standard escape hatch, see the Rerun bullet in root `CLAUDE.md`.
- **Bulk-assign no longer clears the checkbox selection** (`RunExecutionPage.tsx`'s `bulkAssign` mutation) — real user-reported bug: selecting tests, clicking "Assign selected," then trying to also bulk-set a status for that same selection via `bulkResult` found the selection already emptied, forcing the tester to reselect the identical tests a second time. `bulkAssign`'s `onSuccess` was clearing `selectedIds` unconditionally; removed that one line (kept everything else — resetting `bulkAssigneeId`/`filterAssigneeId`, invalidating the tests query). `bulkResult`'s own `onSuccess` still clears the selection, which is correct — that's normally the last step in an assign-then-status sequence. This is a different situation from the "visible list changed → clear stale selection" pattern used elsewhere (`FilterByUser`'s `onApply`/`onClear` here, and the Cases page's bulk bar) — those clear because the SET of visible/selectable items changed underneath the user; a same-page bulk assign doesn't change which tests exist, so carrying the selection forward is the correct behavior, not a footgun.
- **The Reports tab has a genuine print *template*, not just print CSS on the interactive view — this took two attempts to get right, and the first attempt looked worse than doing nothing.** First pass just stripped card borders/shadows/backgrounds via `.print-card { border: none; ... }`, reasoning that a "real report" (per TestRail's own doc: "format the data for you as a report") shouldn't look like a webpage. Screenshotting the actual print output (not just checking computed styles programmatically, which had looked fine) showed this was wrong — content floated as unstructured loose text with no visual grouping at all, worse than the original bordered-card look, plus a duplicate title (the on-screen `<h2>` was never hidden, so it stacked above the new print-only header). Fixed by screenshotting print output at every step and iterating against what it actually looked like:
  - `ReportShell.tsx`: the on-screen title/description block gets `print:hidden` (was showing twice, stacked above the dedicated print header).
  - `.print-card` keeps a real border in print (`border: 1px solid #94a3b8`, not `border: none`) — squared off (no radius/shadow/tint) so it still reads as "grouped data," just document-styled instead of web-app-styled.
  - Row-list cards (`divide-y` on-screen) get `.print-report .print-card > * + * { border-top: ... }` — Tailwind's on-screen divide-y border color (slate-200/700) is deliberately subtle for screen UI and reads as invisible against forced-white print output; this is a separate, stronger override just for print.
  - Section labels (`SummaryReportView.tsx`'s "RUNS IN SCOPE"/"TESTS"/"ACTIVITY") get `print:border-b print:border-black` — put the border on the label's *containing row*, not the label `<p>` itself, when that row also has a sibling action button (e.g. `DownloadCsvButton`) — a border on just the `<p>` only underlines the text width, not the full row, since flex doesn't stretch a text-sized child.
  - Global rules in `index.css`: `print-color-adjust: exact` (without this, browsers strip `background-color` by default when printing — every status bar/badge/priority pill in this app IS a bare `background-color` div with no fallback, so they were printing as blank boxes) and a forced `color: black` on `body *` (dark-mode `dark:text-slate-100` text stays active during print regardless of screen theme, which combined with the forced-white print background is white-on-white and unreadable).
  - Separately, on `RunExecutionPage.tsx` (which already had its own Print button pre-dating the Reports-tab work): checkboxes, the per-test assignee `<Select>`, and the "Edit dates" link were never marked `no-print` and were printing as live, non-functional form widgets. The `Select` needed its *whole wrapper* (`<span className="no-print"><Select>...</Select></span>`), not just a class on the `<select>` itself — `components/Input.tsx`'s `Select` renders its dropdown chevron as a sibling icon in its own wrapper div, outside where the `<select>`'s own `className` prop reaches, so hiding only the `<select>` left a stray floating chevron. A plain-text `print:inline` fallback replaces the assignee select for print.
- **Mutations that change run/result data must also invalidate `['reports']`.** Real user-reported bug, systemic across every report: `queryClient` is configured with `staleTime: 10_000` and `refetchOnWindowFocus: false` (`lib/queryClient.ts`) — reasonable defaults, but they mean a report query, once fetched, does NOT silently self-refresh; it only updates when something explicitly invalidates it. `RunExecutionPage.tsx`'s `submitResult`/`bulkResult`/`closeRun`/`reopenRun`/`rerun`/`bulkAssign` and `PlanDetailPage.tsx`'s `addRun`/`rerunPlan` all mutate data that reports summarize, but none of them invalidated the `['reports', ...]` query namespace — only their own page's own query keys (`['runs', ...]`, `['plans', ...]`). A report tab opened before a run was closed (or before results were submitted) kept showing stale — including empty — data indefinitely, with no way to notice short of a hard reload. Fixed by adding `queryClient.invalidateQueries({ queryKey: ['reports'] })` to each of those mutations' `onSuccess` — this is a prefix match, so it invalidates every report query regardless of its specific scope/params in one call. If you add another mutation that changes run/result/case data a report could summarize, add this same line rather than assuming report tabs will pick up the change on their own.
- **Custom result statuses — a confirmed real gap, not yet built.** TestRail's "Update test results" doc states statuses can be customized beyond the four defaults ("mark outcomes such as Passed, Failed, Blocked, or customise statuses to match your workflow"). `ResultStatus` is a hardcoded union (`PASSED`/`FAILED`/`BLOCKED`/`RETEST`/`UNTESTED`) threaded through nearly every part of the app — badges, filters, reports, `StackedStatusBar`'s palette, the Kanban-style execution buttons. Unlike a single-page addition, this touches the whole app's status model, so it wasn't silently built alongside the smaller gaps above; flag it for a scoped decision (a real `ResultStatus`-config feature, or explicitly out-of-scope like the generic custom-fields engine) before starting it.
- **Per-step result history is skipped entirely (not just hidden-but-present) when every step is still at its default `UNTESTED` with no `actual` text** — e.g. after a quick "Pass & Next" that never touched per-step detail. Showing a wall of "UNTESTED" step badges next to the overall "PASSED" result badge read as an unexplained second status, not as "no per-step detail was recorded." When it does render, it's now labeled "Per-step" so it can't be misread as a competing overall status.
- **Narrowing a `Select` below its default `w-full`**: `components/Input.tsx`'s `Select` always carries `w-full` (from `FIELD_CLASSES`) and renders its own `appearance-none` + a manually-positioned chevron via a `<div className="relative">` wrapper. Passing a competing `w-*` in `className` (e.g. `w-32`) to try to narrow it is a same-specificity conflict with `w-full` — which one wins depends on Tailwind's compiled-CSS order, not on the order of classes in your string (same hazard as the `Badge` bug above; confirmed via `getComputedStyle` in `RunExecutionPage`'s per-step status select, where `w-32` silently lost to `w-full` and clipped "UNTESTED" to "UNTESTE"). The reliable fix is a width-constrained wrapper div around the `<Select>` (`<div className="w-32 shrink-0"><Select .../></div>`) — `w-full` then resolves unambiguously against that wrapper's explicit width instead of fighting `w-full` for the same property. Give the sibling it shares a flex row with `flex-1` so it takes the remaining space. Reuse this pattern for any future narrow/compact `Select`, don't reach for a `w-*` override on the `Select` itself.

## Full-application audit — client-side patterns worth reusing

A systematic bug/design audit (parallel agents per subsystem, empirical live verification — see root `CLAUDE.md`) found and fixed several client-side bugs beyond the server-side ones in `server/CLAUDE.md`. The patterns below are worth remembering so the same *class* of bug doesn't reappear.

- **A `useState(initial?.field)` initializer only runs once, at mount — it does NOT re-derive when a sibling piece of form state (like a template-select dropdown) changes later in the same session.** `CaseForm.tsx`'s `textSteps` field was seeded by a condition on `initial?.template` (`initial?.template !== 'STEPS' ? ... : ''`), which only reflects the template *at mount time* — switching the Template dropdown afterward doesn't re-run that initializer. A real, reproduced data-loss bug lived here: opening a multi-step STEPS case and switching the dropdown to TEXT left the TEXT box seeded empty (mount-time condition was still "STEPS"); saving that empty state omitted `steps` from the request (server correctly treats an absent key as "don't touch"), which *looked* harmless, but reopening the now-TEXT-labeled case re-seeded from a different, now-true condition (`initial.steps[0].step`), and the very next save — even with zero further edits — wrote that single truncated value over the real multi-step data. **The fix wasn't a `useEffect` to resync on every template change** (that would clobber genuinely-typed content when a user toggles back and forth before saving) **— it was seeding the initializer from a function that produces the correct value regardless of which template happens to be selected at mount** (`stepsToText(initial?.steps)` instead of a template-conditional shortcut), so there's no stale-condition window at all. If you see a `useState(initial?.x ? y : z)` pattern gating on a DIFFERENT field's value, check whether that gate can go stale relative to live form state.
- **A field the user can legitimately want to *clear* must be submitted as its real empty value, not coerced with `value || undefined`.** `apiFetch`'s `JSON.stringify` drops `undefined`-valued keys entirely, and the server's `.partial()` PATCH schemas correctly treat an absent key as "don't touch this column" — so `preconditions || undefined` meant a tester who deleted a field's content and saved got a silent no-op, with a success toast and no indication the old value was still there server-side. Same root cause hit `steps`/`bddLines` one level deeper: `textToSteps('')`/`textToBddLines('')` returned `undefined` for an emptied textarea (not `[]`), so clearing all of a case's steps couldn't be saved either. Fixed by (a) sending the field's literal current value including `""` when it applies to the current template, and (b) changing `textToSteps`/`textToBddLines` to return `[]`, never `undefined`, for empty input — `[]` is a real "clear it" value the server correctly applies, `undefined` is "don't touch." The one place `undefined` is still correct is the template-applicability gate itself (`hasStepFields ? preconditions : undefined`) — that's a different question ("does this field even apply to the selected template") from "did the user clear it," and conflating the two was never the bug.
- **A date/data-inheritance chain that's documented as N levels deep needs the *nested* relation actually fetched at every level, not just re-derived client-side from what's already in the payload.** Root CLAUDE.md described "Milestone → Plan → Run" as a real fallback chain, but `GET /runs/:id` only ever selected `plan: { startDate, endDate }` (the plan's own literal fields) and the run's own *direct* `milestone` — never `plan.milestone`. Since a run created under a plan never copies that plan's `milestoneId` onto its own `milestoneId` (see server `CLAUDE.md`), a run whose plan itself *inherits* a date from its milestone had no data path to that date at all — it fell straight to "No dates set" even though the milestone was one click away on the Plan page, which resolves the identical single hop correctly. This showed up independently in three places that all needed the identical two-part fix (nest `plan.milestone` in the server query, then extend the client's fallback chain to check `run.plan?.milestone?.field` before `run.milestone?.field`): `RunExecutionPage.tsx`'s date-inheritance display + its amber over-date warning (both now go through one shared `effectiveEndDateInfo(run)` helper so they can't drift from each other), and `MyTestsPage.tsx`'s `effectiveStartDate`. If you add a fourth level to any inheritance chain, or a new page that resolves an existing one, grep for the two existing "effective date" functions above and match their exact fallback order rather than re-deriving a shorter one.
- **A "selected items" `useState` array that's fed from a live query (config groups, sections, labels — anything a user can delete elsewhere in the same session) needs a `useEffect` that reconciles it against the current query data, not just a manual clear on the obvious UI actions.** `PlanDetailPage.tsx`'s `configIds` had no such effect: deleting a config value via "Manage configurations" (opened in a `Modal` *on top of* the still-mounted Add-Run form) left its id sitting in `configIds` with no visible checkbox for it, silently corrupting both the displayed "Create N runs" count and the actual submit (which 404'd on the stale id). Fixed with `useEffect(() => { const valid = new Set(freshData.flatMap(...)); setSelected(prev => prev.filter(id => valid.has(id))); }, [queryData])`. This is the same "visible list changed → drop stale selection" principle already applied elsewhere in this codebase (bulk case ops, run-execution bulk-assign) — the gap here was that a *second* form (the config manager) mutating shared data while a *first* form stayed mounted wasn't covered by either of those existing effects.
- **Two mutations meant to happen together as one user action (e.g. "reassign, then submit a result") must be sequenced with `await`/`mutateAsync`, not fired as two independent `.mutate()` calls — and each needs its own `onError`.** `RunExecutionPage.tsx`'s `submitStatus` used to call `reassign.mutate(...)` and `submitResult.mutate(...)` back-to-back with no ordering guarantee and no error handling on either — a failure in the reassign had no visible effect beyond the button re-enabling, and the two requests could land in either order. Fixed by awaiting `reassign.mutateAsync(...)` first (only when the dropdown actually changed) inside a try/catch that shows a toast and returns early on failure, so `submitResult` only ever fires after a successful reassign (or no reassign was needed). Any future "do X then Y as one user-visible action" needs this same await-with-error-handling shape, not two sibling `.mutate()` calls.
- **A local state value that mirrors a server field (`submitAssigneeId` mirroring `test.assignedTo?.id`) needs a `useEffect` resyncing it to the prop/query value, not just a `useState` initializer** — otherwise a failed mutation (or any other out-of-band change to the underlying data) leaves the local value permanently out of sync with what the server actually has, with no way for the UI to self-correct. Added `useEffect(() => setSubmitAssigneeId(test.assignedTo?.id ?? ''), [test.assignedTo?.id])` alongside the sequencing fix above.
- **Milestone-to-milestone date inheritance (the `parentId` self-relation) is a *different* gap from the Milestone→Plan→Run chain fixed in the bullet above — both needed fixing independently.** A child milestone with no own `startDate`/`dueDate` used to display nothing at all, unlike every other level of the inheritance chain, which always showed an "Inherits..." fallback. Fixed with a small `effectiveDates(m, byId)` function in `MilestonesTab.tsx` that walks up the `parentId` chain via a `Map<id, Milestone>` built from the already-fetched flat list (`byId = new Map(milestones.map(m => [m.id, m]))`), returning the nearest ancestor's date plus whether it was inherited — `computeStatus` was extended to take this resolved-effective-dates object (not the raw milestone) as its second argument so `Overdue` is computed against the *effective* due date, not just the milestone's own possibly-null one. The same pass added the `Overdue` status itself (a past `dueDate`, not completed — checked after `isCompleted` but before the Upcoming/Open split) and switched the parent-picker `<select>` from iterating the raw flat `milestones` array to iterating the same `tree` structure the list itself renders, with `` `${'—'.repeat(m.depth)} ${m.name}` `` labels — copied directly from `SuiteDetailPage.tsx`'s existing section parent-picker, not a new indentation convention invented for this.

## Pagination and code-splitting (optimization pass)

No dedicated performance work had been done before this pass — see root `CLAUDE.md`'s Roadmap for the full narrative and real load-test numbers.

- **"Load more," not page-number pagination** — every list endpoint that got server-side pagination (cases, runs, webhook deliveries, activity log) is consumed client-side via `useInfiniteQuery`, not `useQuery` + a page-number control. Each `fetchNextPage()` **appends** to the same flat array (`data.pages.flatMap(p => p.cases)`) rather than replacing the current page's rows — this matters specifically for `SuiteDetailPage.tsx`, where bulk-select and drag-and-drop both operate against a single `allCases` array; page-number pagination (swapping which rows are visible) would have silently broken "select some cases, then load more, then bulk-edit the whole selection" and drag targets that scroll past the initial page. `components/LoadMoreButton.tsx` is the one shared presentational piece (`Showing N of Total` + a `Load more` button, hidden entirely once `hasMore` is false and nothing was ever loaded) — reuse it directly for any future paginated list, don't build a second one. The pattern at each call site: `useInfiniteQuery({queryKey, queryFn: ({pageParam}) => api.listX(id, pageParam), initialPageParam: 1, getNextPageParam: (lastPage) => lastPage.hasMore ? lastPage.page + 1 : undefined})`, then `const allX = data?.pages.flatMap(p => p.x) ?? []` and `const lastPage = data?.pages[data.pages.length - 1]` for the `LoadMoreButton`'s `total`/`hasMore` props.
- **Not every paginated API needs "Load More" wired in at every call site — `RunCheckboxList.tsx` is the one deliberate exception.** It's a report's run-picker, already rendered inside a small `max-h-40 overflow-y-auto` scrollable container, and needs *every* run in the project to choose from, not just the first page. Rather than nesting a Load More button inside an already-scrolling list (awkward UX), it just requests a large page directly (`listRuns(projectId, 1, 200)`, the server's max `pageSize`). Default to this "request a big page" shape for any other small, already-scrollable picker; default to real Load More for a primary content list.
- **A picker/selector call site can silently regress to "only sees the first page" if you paginate the underlying API without checking every caller.** `listRuns` gained pagination for `RunsListPage.tsx`'s primary list, but `RunCheckboxList.tsx` was a second, easy-to-miss caller of the same function — grep for every call site of an API function before/after adding pagination params to it, not just the one page you set out to fix.
- **Route-level code-splitting** (`App.tsx`) — every page-level route component is `React.lazy(() => import('./path').then(m => ({default: m.ComponentName})))` (named exports need the `.then` adapter; `React.lazy` requires a default export), wrapped per-route in `Suspense` via a small `withSuspense()` helper — **not one `Suspense` around the whole `<Routes>` block**. Wrapping each route individually means `AppShell`'s header/sidebar (which React reconciles in place across a route change, since it sits at the same position in the tree on every route) stays mounted and visible while only the inner content area shows the loading fallback — a single top-level boundary would flash the *entire* screen, including chrome that isn't actually changing, on every navigation. `ProtectedRoute`, `AppShell`, `AuthProvider`, `ThemeProvider`, `ToastProvider`, and `queryClient` stay eagerly imported (small, shared shell code, not worth their own chunk). Cut the single production bundle from 543 KB (146 KB gzip) to a 266 KB (84 KB gzip) entry chunk plus roughly 40 on-demand page chunks — verify with `npm run build -w client` (not bare `tsc`, see the Verification section above) and check for Vite's "chunks larger than 500 kB" warning disappearing from the build output.

## Verification
There's no client test suite yet. Every feature (auth, case CRUD, runs/execution, plans/milestones, reporting, CSV import/export, webhooks, admin UI) was browser-verified with one-off Playwright driver scripts (not checked into the repo) exercising the real flow end to end, including a reload-and-check-persistence step. If you touch any of these flows again, re-verify in a real browser rather than trusting typecheck alone — that's exactly how the refresh-token concurrency bug (see root `CLAUDE.md`) was caught; typecheck and the server test suite both passed while that bug was live.
- **`npx tsc --noEmit` (bare, no `-p`) is NOT a reliable way to typecheck this project — it silently checks almost nothing.** `client/tsconfig.json` uses TypeScript project references (`"files": []` with only `references` to `tsconfig.app.json`/`tsconfig.node.json`), so a bare invocation doesn't pick up `tsconfig.app.json`'s actual settings, including `noUnusedLocals`/`noUnusedParameters`. Confirmed the hard way: a bare `tsc --noEmit` reported clean while `npm run build -w client` (the project's real build, `tsc -b && vite build`, and what CI actually runs) failed on 3 genuine errors — a loosely-typed `priority?: string` that should have been the `Priority` union (`MatrixTable.tsx`, `defectsResultsReports.ts`), a named interface passed where a `Record<string, X>` generic was expected without an index signature (`summaryReports.ts`'s `SummaryActivityDay`), and an unused `timerTick` state value (`RunExecutionPage.tsx`, fixed via destructuring elision — `const [, setTimerTick] = useState(0);` — since only the setter was ever used). Always typecheck via `npm run build -w client` (or `tsc -b` directly), never bare `tsc --noEmit`.
