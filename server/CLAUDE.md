# TestForge — server

See the root `CLAUDE.md` for overall project context, data model rationale, and auth design. This file covers server-specific conventions.

## Conventions
- **Vertical-slice modules**, not layered MVC: `src/modules/<resource>/{routes.ts,service.ts,schema.ts,*.test.ts}`. Add a `service.ts` when a resource's logic grows past what belongs inline in a route handler (see `auth`, `cases`, `runs`, `sections`, `plans` for examples); thin-CRUD resources (`milestones`, `webhooks`) are routes-only.
- **Delete-impact preview pattern**: any destructive delete with real blast radius exposes a paired `GET .../:id/delete-impact` endpoint returning the counts of what would be destroyed (see `suites/routes.ts`, `sections/routes.ts`, `projects/routes.ts`), which the client fetches to populate a `ConfirmDialog` before the user commits. Add one of these whenever a new delete route can destroy more than the single row it's called on.
- **Many-to-many tag pattern** (`Label`/`TestCaseLabel` in `modules/labels/`): an explicit join model, not Prisma's implicit many-to-many — needed because `TestCaseLabel` is the natural place to add per-assignment metadata later (Test-level labels are the known next step) and because explicit join tables are easier to reason about in general. Case-insensitive uniqueness is checked at the app layer (`assertNameAvailable` in `labels/routes.ts`) since Prisma's `@@unique` can't express case-insensitivity directly on either database engine this project has run on — Postgres's default `text`/`varchar` collation is case-sensitive too (it would need an explicit `citext` column or a functional index to get DB-level case-insensitivity), so this app-layer check stays necessary post-migration, not just a SQLite-era leftover. Replace-all label assignment (`setCaseLabels` in `cases/service.ts`) always deletes-then-recreates the join rows in one transaction rather than diffing — simpler, and the row count per case is capped at 10 so it's cheap.
- **Nested vs. flat routers per resource**: list/create typically live on a router mounted under the parent path (e.g. `suitesNestedRouter` at `/projects/:projectId/suites`), while get/patch/delete live on a router mounted at the resource's own path (e.g. `suitesRouter` at `/suites/:id`). `runs` additionally has a third mount point, `runsByPlanRouter` at `/plans/:planId/runs`, for creating a run scoped to a plan. See `src/app.ts` for the full mount order.
- **"Tests" vs "RunCase"**: TestRail calls a case's execution-within-a-run a "Test" (to distinguish from the source `TestCase`). The Prisma model is `RunCase` (clearer in a JS codebase where "test" collides with testing-framework vocabulary), but it's exposed at the `/api/v1/tests/:id` URL for parity with TestRail's own API surface — see `src/modules/results/routes.ts`.
- **All "enum" fields are `String` in Prisma, not native Postgres `enum` types, even though Postgres (unlike the SQLite this schema originally targeted) supports them.** This was a hard SQLite constraint originally; post-migration it's a deliberate choice to keep the provider swap scoped to "same columns, new engine" rather than bundling in a real column-type migration with data backfill for every affected field (see root `CLAUDE.md`'s Roadmap — that conversion is tracked separately, not done). Validated by Zod schemas in each module's `schema.ts` and typed via literal unions (`src/types/roles.ts` for `Role`; case/priority/type/status literals live inline in each schema file). If you add a new enum-like field, follow this same String-plus-Zod pattern for consistency with every existing one, not a Prisma `enum` — until/unless the native-enum conversion above actually happens.
- **Errors:** throw `AppError` subclasses from `src/lib/errors.ts` (`UnauthorizedError`, `ForbiddenError`, `NotFoundError`, `BadRequestError`); the global `errorHandler` middleware converts them (and `ZodError`) to JSON responses. Wrap async route handlers in `asyncHandler` from `src/lib/asyncHandler.ts` so thrown errors reach it.
- **CSV** (`src/lib/csv.ts`) is a small hand-rolled RFC4180-ish encoder/decoder — no dependency, handles quoting/embedded commas/newlines. Rows join with `\r\n`, not `\n` — if a test asserts against a specific line, split on `\r\n` or it'll pick up a trailing `\r`. Case import/export (`src/modules/cases/csv.ts`) auto-creates sections by name (case-insensitive match against existing sections) and round-trips steps via the same `"step | expected"` line format the client's case-form textarea uses (`src/modules/cases/stepsFormat.ts`).
- **Sections Hierarchy import/export** (`src/modules/cases/csv.ts`) — the section column is read as a `>`-delimited path (`Parent > Child`), matching TestRail's own distinct "Sections" (flat name) vs. "Sections Hierarchy" (full path) column concept; a plain name with no `>` behaves exactly as the old flat format did, so this is backward compatible with hand-authored CSVs. `routes.ts`'s `resolveSectionPath` walks the path level by level, keyed by `${parentId}::${name.toLowerCase()}` so same-named sections under different parents don't collide — reuse this keying scheme (not a flat name-only map) for any future by-name section resolution that needs to respect nesting. Export always emits the full ancestor path via `buildSectionPathMap`'s recursive per-section parent-walk (memoized in a `Map`, not recomputed per case), so export → reimport round-trips the same tree shape.
- **Export column picker** (`GET /suites/:suiteId/cases/export`'s `columns` query param, `resolveExportColumns` in `cases/csv.ts`) — `title` is always force-included server-side regardless of what the client requests, since a row with no title can't be matched to anything on reimport. Don't rely on client-side validation alone for this; the server is the actual guarantee.
- **Webhooks** (`src/lib/webhook-dispatcher.ts`) fire synchronously within the triggering request (run create/close) — fine at this scale, but if delivery volume ever matters, this is the spot to move to a queue. Each attempt is HMAC-SHA256 signed (`X-TestForge-Signature`) and logged to `WebhookDelivery` regardless of success/failure, with a 5s timeout via `AbortSignal.timeout`.
- **OpenAPI spec** (`src/openapi/spec.ts`) is hand-authored, not generated from the Zod schemas — if a route's request/response shape changes, update the spec by hand. Served at `/api/v1/docs` (Swagger UI) and `/api/v1/openapi.json`.
- **Defects are derived, not stored as their own entity** — there's no `Defect` table. `src/modules/reports/routes.ts`'s `defectsRouter` aggregates them on the fly from `Result.defects` (comma-split, grouped in JS, not SQL — SQLite/Prisma has no clean groupBy-after-split) by walking each `RunCase`'s *latest* result only. `src/modules/runs/defectsCsv.ts` follows the same "latest result only" rule when building the bulk CSV export. If you ever add a real `Defect` table, this aggregation logic becomes redundant — don't keep both.
- **Batch result entry** (`POST /runs/:id/tests/bulk-result`) submits one status to many tests at once: one `Result` per test via `createMany` (each needs a distinct row, unlike a plain field update) plus one `updateMany` for the denormalized `RunCase.status` — same create-then-flip-status shape as the single-test submit endpoint, just batched. No `stepResults`/`defects` fields — a batch action is for "these all passed/failed identically," not per-step or per-defect detail.
- **Bulk operations use `updateMany`, not a loop of individual updates** — `POST /runs/:id/tests/bulk-assign` (`src/modules/runs/routes.ts`) takes a `testIds` array and does one `prisma.runCase.updateMany({ where: { id: { in: testIds }, runId: ... } })` call. The `runId` in the `where` clause is what scopes it safely — a test id from a different run is silently ignored (counted in the response's `updated` total as not-matched) rather than erroring, so double-check `updated` client-side if you need to detect partial application. The same pattern now covers cases too (`PATCH /cases/bulk-update`, `POST /cases/bulk-delete`, `POST /cases/bulk-add-labels` in `cases/routes.ts`).
- **A literal-segment route (`/bulk-update`, `/delete-impact`, etc.) must be registered *before* a same-method `/:id` route on the same router**, or Express's registration-order matching lets `/:id` swallow it (`id="bulk-update"`). Bit the project once already on `PATCH /cases/bulk-update` vs `PATCH /cases/:id` — when adding a new literal route alongside an existing `/:id` of the same HTTP method, check registration order, not just that the route compiles.
- **`prisma.<model>.createMany({ skipDuplicates: true })` is now usable — it was a Postgres/MySQL-only option that SQLite rejected at compile time, back when this schema targeted SQLite.** `bulk-add-labels` in `cases/routes.ts` still queries existing rows first and filters them out in application code before `createMany`, the pattern that SQLite forced — that code is correct and doesn't need to change just because a shorter option now exists (don't churn working code for its own sake), but a *new* idempotent/dedup bulk-insert can reach for `skipDuplicates: true` directly instead of re-deriving the manual filter-first pattern.
- **Reorder-via-move pattern** (`moveSection` in `sections/service.ts`): rather than computing a single row's new `orderIndex` from index-shift math (easy to get off-by-one, and drifts after repeated moves), fetch the full sibling list at the target parent, splice the moved item into the desired position in memory, then re-write every sibling's `orderIndex` to its new array position (0..n-1) in one transaction. Also checks for cycles (`collectSectionSubtree`) before allowing a reparent, since `Section.parent`'s `onDelete: Restrict` doesn't protect against a self-referencing loop on its own. Reuse this pattern for any other orderable/nestable resource (e.g. Milestones, once drag-and-drop reaches them).

- **Runs list includes a per-run status breakdown** (`GET /projects/:projectId/runs`) — reuses `runs/service.ts`'s existing `getRunSummary(runId)` (already used by the single-run summary endpoint) via `Promise.all` over the list, the same "N `groupBy` calls in parallel" pattern `reports/routes.ts`'s `dashboardRouter` already uses for its "Recent runs" widget. Added because the Runs list (where you actually pick which run to work on) was showing *less* status info than the Overview dashboard summarizing it — a real UX gap caught during a design pass, not a performance concern at this scale.
- **`/me/workload` (Phase K) is Admin/Lead-only, unlike its sibling `/me/tests`** — `/me/tests` defaults to the caller's own data and only allows `?userId=` for privileged roles, but workload is inherently cross-user (a bar-per-assignee chart), so there's no sensible "self" default to fall back to; it 403s outright for TESTER/VIEWER rather than silently scoping to just the caller. Uses `runCase.groupBy({by:['assignedToId']})` scoped to `run.isCompleted:false`, matching the same "active run" convention `/me/tests` already uses.
- **Summary report scope resolution** (`src/modules/reports/summaryReports.ts`'s `resolveScopeToRunIds`) — Milestone/Plan/Project/Runs are structurally different scopes, resolved into a flat run-id list once so the aggregation core doesn't branch on scope type. Milestone scope is a real `OR` union (`{milestoneId} | {plan:{milestoneId}}`) since a `TestRun` created under a plan does NOT get that plan's `milestoneId` copied onto its own `milestoneId` field — a milestone-scoped report that only checked `TestRun.milestoneId` directly would silently miss every run added via a plan. Runs scope is an explicit id array that returns empty (not "recent runs") when nothing is selected — the one report in this whole family where an empty selection means "show nothing," not "default to something reasonable," because unlike the other run-scoped reports there's no sensible implicit default for "pick some runs to summarize."
  - **Project scope is `TestRun.projectId` directly — it does NOT go through milestones.** A real user-reported bug lived here: the original implementation resolved "project scope" by fetching every milestone in the project and OR-ing their milestone/plan-milestone matches (the same shape as milestone scope, just looped) — so a run created without a milestone attached, the ordinary case for a lot of real usage, never appeared in its own Project Summary report even after being closed with real results reported ("i already closed a run but it is empty"). The bug was even codified as "expected" in a test (`summaryReports.test.ts`'s old "excluding fully unscoped runs" assertion) — a reminder that a regression test can just as easily lock in wrong behavior as right behavior if the underlying assumption was never questioned. `TestRun` has always had a direct, non-nullable `projectId` field; there was never a reason to route through milestones for this scope at all.
- **Mount-path naming to avoid Express prefix ambiguity**: `/reports/summary` (project scope) and the sibling explicit-runs-scope report are mounted as `/reports/runs-summary`, not `/reports/summary-runs` — deliberately so neither mount path is a string-prefix of the other, sidestepping any doubt about whether Express's `app.use()` prefix-matching is segment-boundary-aware. Verified via a dedicated test (`summaryReports.test.ts`'s "do not collide" case) that both resolve independently rather than one swallowing the other. Apply the same naming discipline (rearrange words, don't rely on matcher internals) if two sibling mount paths ever risk this again.
- **Cases×runs matrix** (`src/modules/reports/runsMatrix.ts`) — the shared query behind 4 of the 6 Defects/Results reports (Summary for Cases/References, Comparison for Cases/References): one `runCase.findMany({where:{runId:{in:runIds}}, select:{...}})` call, pivoted in JS into `Map<caseId, Map<runId, cell>>`. Two variants exist — `buildCasesRunsMatrix` (status only) and `buildCasesRunsMatrixWithDefects` (adds a `results:{take:1}` select for cell-level defect IDs) — as two separate, independently-typed Prisma queries rather than one function branching on a boolean, since Prisma's `select`-shape return type differs per query and trying to share one function would need an `as any` cast to reconcile the two shapes. Add a third variant the same way (a new function, not a flag) if a future report needs yet another cell shape. `aggregateDefects`/`fetchLatestResultPerRunCase` in the same file generalize the original `defectsRouter`'s inline defect-rollup logic — that router now calls these instead of duplicating the aggregation, so there's one implementation, not two.
- **Report aggregation is hand-rolled, not a stats/charting library** (`src/modules/reports/aggregation.ts`) — `groupByField`/`bucketByPeriod`/`resolveDateRangePreset` operate on plain Prisma `findMany` results via JS `Map`/`reduce`, matching this project's existing no-dependency philosophy (`lib/csv.ts`, `cases/gherkin.ts`). **All date-bucketing in this file is UTC-consistent throughout** (`Date.UTC`/`getUTCDate`/`setUTCDate`, never local-time `Date` getters/setters) — mixing the two was tried first and produced a real off-by-one-day bug: `periodKey()` derives a bucket key via `date.toISOString()` (always UTC), so if `resolveDateRangePreset`'s day/week/month arithmetic used local-time components instead, a "today" boundary computed in a non-UTC server timezone could serialize into the *previous* UTC calendar day. Matches this codebase's existing convention of treating date-range filters as UTC calendar days (see `CaseFilterBar`'s `T00:00:00.000Z`/`T23:59:59.999Z` suffix convention client-side). If you add another date-bucketing helper, keep it UTC end-to-end — don't reach for local-time `Date` methods anywhere in the chain.
- **Data migrations that change the meaning of an existing column's default need an explicit backfill statement, not just a schema default.** Adding `TestCase.template String @default("TEXT")` gave every pre-existing row `'TEXT'` via the column default, but those rows were all authored under the old always-STEPS-shaped case form — an explicit `UPDATE` was added to the migration SQL (and run once directly against the already-migrated dev database, since `prisma migrate dev` only executes new migration files, not retroactive fixes to one already marked applied) to relabel them `'STEPS'` instead. Reuse this pattern (hand-edit the generated migration SQL to add a backfill) whenever a new column's default doesn't correctly describe data that predates the column.

- **Live-linked vs. snapshot-resolved reads of the same data**: `SharedStepSet` content is deliberately read two different ways depending on caller. `toPublicCase` (`cases/serialize.ts`) resolves a case's attached sets at request time — always current, so editing a set propagates everywhere immediately. `resolveStepsForCases` (`sharedSteps/service.ts`), used only by `runs/service.ts`'s `createRun`, instead flattens everything into a plain array once and writes it into `RunCase.stepsSnapshot` — this is the one place resolution must NOT be live, since runs are immutable history. If you add another feature that reads `SharedStepSet` content, decide explicitly which of these two patterns it needs; defaulting to "live" everywhere would let a shared-step edit retroactively rewrite a closed run's results.

- **No Gherkin/Cucumber library dependency** — `cases/gherkin.ts` is a small hand-rolled line-regex parser (mirrors the project's existing hand-rolled `lib/csv.ts` philosophy: simple format, no dependency, easy to reason about) covering only what TestForge's BDD template needs: `Feature:`, `Scenario:`/`Scenario Outline:` (title only, no Examples table), and `Given/When/Then/And/But` step lines. `@tags` and `Background:` are skipped during parse (so a real-world `.feature` file with them doesn't error) but never stored — if BDD support ever needs to grow into full Cucumber compatibility, this file is where that work starts, not a reason to pull in a library preemptively.

- **Audit log is opt-in per action, not a generic hook** — `lib/audit.ts`'s `logAudit` is called explicitly from the specific route handlers listed in root `CLAUDE.md`'s Activity log bullet, not wired into a global middleware. If you add a new destructive or easily-second-guessed action, call `logAudit` directly after the mutation succeeds rather than trying to generalize this into a catch-all — the deliberate scope is "actions worth a paper trail," not "every mutation."

## Testing
- `npm test` runs Jest+Supertest (233 tests across 34 files as of this writing). `src/test/setup.ts` is a `setupFilesAfterEnv` file that overrides `DATABASE_URL` to a per-test-file Postgres **schema** (namespace, via the URL's `?schema=` param) **before** the test file's own imports run (module-load-order matters here — see the comment in that file) and pushes the schema via `prisma db push`, which auto-creates that Postgres schema if it doesn't exist. Each test file therefore gets an isolated set of tables; don't assume fixtures from one test file exist in another. This replaced an earlier isolated-SQLite-file-per-test-file approach when the project migrated to Postgres (root `CLAUDE.md`'s Roadmap) — same guarantee, Postgres-native mechanism. `afterAll` drops the schema (`DROP SCHEMA ... CASCADE`) rather than unlinking a file.
- Run serially (`--runInBand`, set in `package.json`) since each test file resets its own schema — parallel workers would still be fine given isolated schemas, but serial keeps failures easy to read.
- `src/config/prisma-client.ts` skips its dev-hot-reload `global` caching when `process.env.JEST_WORKER_ID` is set — without this, `global` persists across test files in the same Jest worker and leaks one file's PrismaClient (bound to its own DATABASE_URL) into the next file's tests, causing spurious "table does not exist" errors. If you ever see that error in a *new* test file, check this first before assuming a migration problem.
- Webhook tests (`src/modules/webhooks/webhooks.test.ts`) spin up a real local `http.Server` as a receiver rather than mocking `fetch` — this exercises the actual HTTP delivery path (HMAC signature, timeout, success/failure logging) end to end.

## Optimization pass — pagination, caching, load testing

No dedicated performance work had been done before this pass — see root `CLAUDE.md`'s Roadmap for the full narrative and real load-test numbers. The patterns below are what to reuse for any future list endpoint or expensive read.

- **Pagination convention** (`lib/pagination.ts`) — `parsePagination(query, {defaultPageSize, maxPageSize})` reads 1-indexed `?page=`/`?pageSize=` (clamped: page ≥ 1, pageSize ≤ `maxPageSize`), returns `{skip, take, page, pageSize}` for a direct Prisma `findMany`. `paginationMeta(total, params)` returns `{total, page, pageSize, hasMore}` — spread this alongside the endpoint's existing array key (`{ cases: [...], ...paginationMeta(total, pagination) }`), never replacing it, so every pre-existing caller reading just the array key keeps working unchanged. Always pair the paginated `findMany` with a `prisma.<model>.count({ where })` using the *same* `where` clause, run together via `Promise.all`. Applied to: `GET /suites/:suiteId/cases`, `GET /sections/:sectionId/cases` (`cases/routes.ts`), `GET /projects/:projectId/runs` (`runs/routes.ts`), `GET /webhooks/:id/deliveries`, `GET /projects/:projectId/audit-log`. A hard `take: N` with no `skip` (the pre-pagination shape of the last two) isn't a real limit, it's a silent, permanent ceiling — converting it to real `skip`/`take` with the same default `pageSize` is a pure improvement, not a behavior change for any caller that never asks for page 2.
- **A report/rollup endpoint that aggregates across "every run" must use the same scope-resolution convention its siblings do, not its own unbounded query.** `GET /projects/:projectId/defects` (`reports/routes.ts`) was the one report in the whole Defects/Results family that skipped `runsMatrix.ts`'s `resolveRunIds` (explicit `?runIds=`, else the 25 most recent runs) — an unbounded scan over the project's entire RunCase history. Fixed to call `resolveRunIds` like every sibling report. If you add a new report/rollup endpoint, start from `resolveRunIds`, don't write a fresh unscoped query and assume pagination alone will fix the cost later — pagination only bounds the *response*, not the *query*.
- **A nested array inside a paginated row is a second, independent growth axis pagination of the outer array doesn't touch.** Each `DefectEntry.cases[]` (one entry per occurrence of that defect) can grow large on its own even with the top-level `defects[]` list paginated — capped at `MAX_CASES_PER_DEFECT` (50) with the real count exposed as `casesTotal`, so the client can tell "capped" apart from "that's really all of them." Check for this shape (an array nested inside an already-paginated row) whenever you paginate a new endpoint.
- **In-memory TTL cache** (`lib/cache.ts`) — `getOrSetCache(key, ttlMs, fn)`, hand-rolled (no Redis/node-cache dependency, matching `csv.ts`/`gherkin.ts`'s existing no-dependency philosophy), skip-guarded under Jest via the same `JEST_WORKER_ID` check `rateLimit.ts` already established (a cached response from one test would otherwise leak into the next test sharing the same in-memory store/process). **Read-through, not write-invalidated** — entries expire on their own after `ttlMs` rather than being explicitly cleared by the mutations that would affect them; deliberate, since wiring real invalidation into every scattered mutation call site (every result submission, run close, case edit, bulk operation) would be a much larger and easier-to-get-wrong change than accepting a short staleness window. Only cache data where "correct within the last `ttlMs`" is an acceptable tradeoff (reports/dashboards, not a record a client just wrote and expects to read back immediately). Applied to `dashboardRouter`/`crossProjectDashboardRouter` (`reports/routes.ts`) at a 30s TTL — both were refactored from an inline route handler into a standalone `buildProjectDashboard`/`buildCrossProjectDashboard` function first, so the cache wrapper is just `getOrSetCache(key, ttl, () => buildX(...))` around a plain data-returning function, not tangled into `res.json()` calls.
- **Load-testing script** (`scripts/loadtest.ts`, run via `npm run loadtest -w server`) — targets a live dev server (not Jest), seeds its own throwaway project/cases/runs, measures cold-vs-warm cache latency plus sustained-load req/s via `autocannon`, then deletes its fixture project. Not part of `npm test` or CI — this measures wall-clock performance against a real running process, a different kind of check than correctness tests. **Bypasses rate limiting via `LOADTEST_MODE=true`**, read only by `rateLimit.ts`'s own `isTest` check (`!!process.env.JEST_WORKER_ID || process.env.LOADTEST_MODE === 'true'`) — a server-process environment variable, never anything a request itself can set (a header or query-param bypass would be a real, request-controllable vulnerability; this isn't one, since production never sets this env var). To run: stop the dev server, restart it with `LOADTEST_MODE=true` set in the shell that launches it, run `npm run loadtest -w server`, then restart the dev server again *without* the env var so rate limiting is back to normal for continued dev use — don't leave a rate-limit-bypassed server running.
- **SQLite serializes transactions against a single writer — a real concurrent-write burst genuinely bottlenecked, confirmed by the load test above at the time it was written, not a hypothetical.** An early version of the load test's fixture setup fired 30 concurrent `POST /runs` requests (`createRun` wraps its work in a Prisma `$transaction`); several failed with a real `P1008` "operations timed out" error. Cases, by contrast, created fine at even higher concurrency (105-way tested clean) since case-create isn't transaction-wrapped. **This finding directly motivated the Postgres migration below, which is now done** — Postgres's row-level locking/MVCC handles concurrent transactions natively, so this specific bottleneck no longer applies. The load test's own fixture setup was fixed to create runs sequentially rather than parallel regardless (both because that's more realistic — real usage doesn't burst-create 30 runs at once — and so "fixture setup hit a limitation" doesn't get conflated with "the endpoints under test are slow"), so re-running `npm run loadtest -w server` today won't reproduce this even artificially; the historical finding is kept here as the reasoning trail for *why* the migration happened, see root `CLAUDE.md`'s Roadmap for the migration itself.

## PostgreSQL setup (local dev)

The project runs on Postgres, not SQLite (see root `CLAUDE.md`'s Roadmap for the migration story). One-time setup for a fresh machine:

```powershell
# Install PostgreSQL 17 (official installer, not necessarily via winget -- the winget
# community-repo download source, get.enterprisedb.com, was blocked in the sandboxed
# environment this project's migration happened in; a manual download from
# postgresql.org/download/windows worked fine and is the safer default instruction to give
# since winget's default source may or may not be reachable in any given environment).
# Verify the installer's SHA256 against the one winget/postgresql.org publishes before running
# it, same as you would for any executable from the internet.

# Then, one time, create the app's own role + database (not the postgres superuser):
psql -U postgres -c "CREATE ROLE testforge WITH LOGIN PASSWORD 'testforge_dev_pw';"
psql -U postgres -c "CREATE DATABASE testforge OWNER testforge;"
psql -U postgres -c "ALTER ROLE testforge CREATEDB;"  # needed for `prisma migrate dev`'s shadow database
```
`DATABASE_URL` in `server/.env` (see `.env.example`) then points at `postgresql://testforge:testforge_dev_pw@localhost:5432/testforge?schema=public`. The `CREATEDB` grant is a real, if minor, privilege escalation beyond what the app itself needs at runtime (it only ever reads/writes rows) — acceptable for a single-developer local Postgres instance, but don't grant it this liberally on a shared/production database; there, run `prisma migrate deploy` (which doesn't need a shadow database) instead of `prisma migrate dev`.

## Gotchas already hit
- Prisma Client regeneration can hit `EPERM` on Windows if another process (editor TS server, a leftover `tsx` process) holds the query engine `.dll.node` file open. If `prisma migrate dev` reports this, the already-generated client is usually still valid — verify with a quick script (`npx tsx prisma/seed.ts` or similar) before assuming it's broken.
- **Self-relations (`Section`/`Milestone` `parentId`, `onDelete: Restrict`) block cascades that pass through them.** Deleting a Suite or Project cascades to Section via Prisma's declarative `onDelete: Cascade`, but that cascade has no defined child-before-parent order — a suite/project containing a nested (parent+child) section pair throws a raw FK-constraint error, surfaced to the client as a generic 500. Fixed in `suites/routes.ts` and `projects/routes.ts` by `updateMany`-ing the relevant `parentId`s to `null` *before* the cascading delete. This bug only reproduces with actual nesting present, so a flat-structure test won't catch it — see the "nested" regression tests in `suites.test.ts`/`projects.test.ts` for the pattern to copy if you add another self-relation.
- **`express.json()`'s default 100kb body limit is too small for this app's own CSV case-import feature** — a real-world CSV of a few hundred richly-detailed test cases (the exact scenario the importer exists for) comfortably exceeds it, and Express's body-parser rejects the request *before it reaches any route handler*. Worse, that rejection (a `PayloadTooLargeError`, not an `AppError`/`ZodError`) fell through `errorHandler.ts`'s generic catch-all, surfacing to the user as an unexplained "Something went wrong" 500 with no indication it was a size problem — a real user-reported bug, reproduced end-to-end with an actual ~400-case CSV before being root-caused. Fixed two ways: `app.ts` now sets `express.json({ limit: '10mb' })` (real headroom over any realistic import), and `errorHandler.ts` explicitly recognizes `err.type === 'entity.too.large'` and returns a proper `413 PAYLOAD_TOO_LARGE` instead of the generic fallback, so a future request that's *still* too large fails with a clear message rather than repeating this same dead end. See `middleware/errorHandler.test.ts`.
- **A leading UTF-8 BOM in an imported CSV silently breaks section-hierarchy parsing, found investigating the same real CSV import above.** `String.trim()` does not strip `U+FEFF` — left in place, it glues onto the first header cell (`"﻿section"`), which then fails `col('section')`'s exact-match lookup, so `idx.section` resolves to "not found" and every row falls back to a single generic `"Imported"` section regardless of the file's actual `Parent > Child` paths. This fails silently (still `201`, still `imported: N`), not with an error — easy to miss unless you check where the rows actually landed. Fixed in `cases/csv.ts`'s `parseCasesCsv` by stripping a leading `﻿` before parsing. BOM-prefixed files are common (Excel's own CSV export, Notepad's default UTF-8 save, and apparently some AI-generated files) — if you add another CSV/text ingestion path, strip a leading BOM there too rather than assuming this is a one-off.

## Full-application audit — server-side patterns worth reusing

A systematic bug/design audit (parallel agents per subsystem, empirical live verification against the real dev server, not just code reading — see root `CLAUDE.md`) found and fixed ~30 issues across the whole server. The individual fixes are in git history / the PR description; the patterns below are the parts worth remembering so the same *class* of bug doesn't reappear elsewhere.

- **`errorHandler.ts` now maps `Prisma.PrismaClientKnownRequestError` (P2002 unique violation → 400, P2003 FK violation → 400, P2025 not-found → 404), `Prisma.PrismaClientValidationError` → 400, and `multer.MulterError` (`LIMIT_FILE_SIZE` → 413) — this single change fixed a surprising number of independent "raw 500 instead of a clean validation error" findings at once** (duplicate email, duplicate config-group seed values, duplicate bulk-add-labels pairs, an oversized attachment upload, several dangling-foreign-key cases). **If you add a new route that writes user-supplied data straight into a Prisma call with no pre-check, you very likely don't need a bespoke try/catch — this generic handler already covers the common failure shapes.** Only add a specific pre-check when you want a more precise error message than "A record with this X already exists" / "A referenced record does not exist".
- **A cross-entity foreign key accepted from the request body needs an explicit `WHERE id = X AND projectId = callerProjectId` existence check, every time — Prisma doesn't do this for you, and forgetting it is a silent, exploitable-via-direct-API cross-project data leak, not just a 500.** Found and fixed independently in three places that all had the identical gap: `TestRun.milestoneId` (`runs/service.ts`'s `createRun`), `TestPlan.milestoneId` (`plans/routes.ts`, both create and update), and `Milestone.parentId` (`milestones/routes.ts`). A nonexistent id 500'd before the errorHandler fix above (now a clean 404); an id belonging to a *different* project silently succeeded and leaked that other project's data into a response, with no error at all. `runs/service.ts`'s pre-existing `suite.projectId !== projectId` check for `suiteId` was the one place this was already done correctly — copy that shape, not a bare `findUnique`-and-trust-it.
- **`assertRunIsOpen(runId)` (`runs/service.ts`) is the one place "is this run closed" is checked — call it from any new route that mutates a `RunCase` or its `Result`s.** Before it existed, `PATCH /runs/:id`'s date fields were the *only* write path that checked `isCompleted`; submitting a result, reassigning a test, and both bulk endpoints all silently succeeded against a closed run via direct API use, contradicting the execution UI's own "This test run is completed" banner. If you add a sixth way to write to a `RunCase`, call this first.
- **`assertUserExists(userId)` and `assertPublicHttpUrl(url)` (both in `src/lib/`) exist because "accept an id/URL from the request body and trust it" is a recurring gap, not a one-off — reuse them rather than re-deriving the same check.** `assertUserExists` closed four independent unvalidated-`assignedToId` findings; skipping it on a fifth would just reopen the same bug shape. `assertPublicHttpUrl` is the SSRF guard for any outbound-request feature — call it both at registration time (`webhooks/routes.ts`) *and* immediately before every actual delivery (`webhook-dispatcher.ts`), since a hostname's DNS record can change between the two (DNS rebinding) and registration-time-only validation isn't a real guarantee.
- **A `net.isIP()`/URL-hostname check must strip brackets from an IPv6 literal first, and must handle the *hex-group* form of an IPv4-mapped address (`::ffff:7f00:1`), not just the dotted-decimal form (`::ffff:127.0.0.1`) someone would type.** `new URL('http://[::1]/x').hostname` is `"[::1]"` with the brackets still attached, and Node's URL parser silently normalizes a literal `::ffff:127.0.0.1` into the hex-group form — both were caught live by `urlSafety.test.ts` (written *after* the initial fix, which had exactly this bug) before being trusted. If you write another IP-literal safety check, verify it against `new URL(...).hostname`'s actual output, not an assumed string shape.
- **A route accepting `sectionId`/`parentId`-style "move this into that container" input needs to check the target belongs to the same *ancestor scope* the source is already in, not just that it exists.** `TestCase.suiteId` and `TestCase.sectionId` are independent columns (the section doesn't imply the suite) — `PATCH /cases/:id` and `PATCH /cases/bulk-update` accepted a `sectionId` from a *different* suite with zero check, silently splitting a case's `suiteId`/`sectionId` into an inconsistent, half-orphaned state. Fixed by checking `section.suiteId === case.suiteId` (single) / `every case.suiteId === section.suiteId` (bulk) before the write, matching the deliberate "cross-suite move isn't a supported feature" scope call already documented for drag-and-drop.
- **A field with no explicit `orderIndex` on create silently defaults to the Prisma schema default (`0`) for every fresh sibling — "creation order" was never actually guaranteed, just incidentally true on SQLite's unindexed-scan tie-break.** `nextSectionOrderIndex`/`nextCaseOrderIndex` (`sections/service.ts` / `cases/service.ts`) compute `MAX(existing sibling orderIndex) + 1` — not a `COUNT`, which would collide after any deletion leaves a gap — and are now called from every section/case create path, including the CSV and `.feature` import loops (which lazily cache one MAX query per section/parent, then increment in memory across the rest of that import batch, rather than re-querying per row). If you add another orderable/nestable resource, seed its `orderIndex` at create time the same way — don't rely on the schema default plus incidental DB ordering.
- **`moveSection`'s reparent path re-normalizes the *destination* parent's siblings but must also re-normalize the *origin* parent's remaining siblings — a reparent touches two sibling groups, not one.** Missing the origin side left permanent, compounding `orderIndex` gaps there. Reuse this two-group-renormalize shape for any other move/reparent operation on an orderable, nestable resource.
- **A field the client can legitimately want to *clear* (not just "not provide") must be sent as its real empty value (`""`, `[]`), never coerced to `undefined` — `undefined` keys are dropped by `JSON.stringify` and the server's `.partial()` PATCH schemas correctly treat an absent key as "don't touch this column," which is the right contract, but a client that conflates "empty" with "absent" can never use it to clear anything.** This is a client-side pattern (see `client/CLAUDE.md`), but the server-side half of the contract — `updateCaseSchema`'s fields already accept an empty string/array fine, no schema change was needed — is worth knowing before you assume a server-side fix is required for a "can't clear this field" bug report.
- **`DELETE /users/:id/api-keys/:keyId`'s ownership check must scope the actual mutation by *both* ids (`updateMany({ where: { id: keyId, userId: id } })`), not just gate the route entry with a check that the caller owns `:id`.** The pre-fix version checked "does the caller own `:id`" and then updated `:keyId` with no further scoping — any caller could revoke any other user's key by aiming the URL's `:id` at themselves and `:keyId` at the victim's key. This is the general IDOR shape to check for on any nested `/:parentId/:childId` route: confirm the *mutation's* `WHERE` clause references both ids, not just the route guard.
- **A JWT's embedded claims (id, role) must be treated as a *snapshot from login time*, not live truth, for anything security-sensitive — re-read the user from the DB on every request if deactivation/role-changes need to take effect before the token's own TTL expires.** `requireAuth`'s API-key branch already did this (it has no choice — revocation has to be checked live); the JWT branch didn't, so deactivating or demoting a user had no effect on anyone already holding a live token for its full ~15min lifetime. Now both branches re-read.
- **A login (or any credential check) that returns early on "user not found," skipping the password-hash comparison entirely, has a timing side-channel — measure it, don't assume it's negligible.** Confirmed empirically: ~462ms for a real-email/wrong-password failure vs. ~4ms for a nonexistent-email failure, a 120x gap trivially distinguishable in one request pair. Fixed by always running `bcrypt.compare` against a real (dummy) hash when no user exists, so both failure paths pay the same cost — see `lib/password.ts`'s `DUMMY_PASSWORD_HASH`.
- **A read-then-conditionally-write sequence (check `revokedAt IS NULL`, then later write `revokedAt = now`) is not atomic just because it's inside one `async` function — two concurrent requests can both pass the read.** The refresh-token rotation's reuse-detection caught *sequential* replay correctly (the read-time check works fine for that) but not two genuinely parallel requests presenting the same token, since both could read "not yet revoked" before either had written. Fixed by making the claim itself the atomicity boundary: `updateMany({ where: { id, revokedAt: null }, data: {...} })` and checking the returned `count` — 0 means you lost the race, treat it as reuse. Reuse this shape (`updateMany` with the precondition in the `WHERE`, not a separate read-then-write) for any other "exactly one caller should win" sequence.

## Follow-up hardening pass — deferred audit items, now closed

The items above were the original ~30-issue audit. A handful of smaller findings were deliberately deferred at the time (see root `CLAUDE.md`'s former "Longer-standing, still open" list) and closed out in a later pass; the patterns below extend the same reusable-lesson collection.

- **Rate limiting** (`middleware/rateLimit.ts`) is skip-guarded under Jest via `skip: () => !!process.env.JEST_WORKER_ID` — the same "skip in test environment" convention `config/prisma-client.ts` already established for its dev-hot-reload `global` caching. `apiRateLimiter` (300 req/15min) mounts on the whole `/api/v1` prefix in `app.ts`; `loginRateLimiter` (10 req/15min, a stricter anti-brute-force limit) mounts only on `POST /auth/login` in `auth/routes.ts` — don't also import it into `app.ts`, ESLint will flag it unused there since it's applied at the route level, not globally. Because the exported limiters are permanently skip-guarded inside this Jest process, a regression test can't observe them in *enforcing* mode directly — `rateLimit.test.ts` instead validates the exact recipe (windowMs/limit/standardHeaders/message shape) on a throwaway, non-skip-guarded instance, plus a separate functional check that the real exported singletons stay silent under `JEST_WORKER_ID`.
- **Last-admin lockout** (`users/routes.ts`) — `wouldLoseAdminStatus(target, patch)` checks whether an incoming PATCH/DELETE would take the target from active-ADMIN to not-active-ADMIN, and `assertOtherActiveAdminExists(excludingUserId)` then confirms at least one *other* active admin exists before allowing it. Both `PATCH /:id` and the deactivate-on-`DELETE /:id` call this before writing. If you add a further way to change a user's role/active status, route it through these two helpers rather than re-deriving the check. `lastAdminLockout.test.ts` deactivates every admin at the top of each solo-admin test (`deactivateAllAdmins()`) rather than relying on file/test ordering — a *rejected* PATCH/DELETE correctly leaves its admin still active, so admins accumulate across tests in the same file unless each test resets to a known "exactly one admin" starting point itself.
- **Webhook replay protection** (`lib/webhook-dispatcher.ts`) — `sign()` now HMACs `${timestamp}.${body}` instead of `body` alone (Stripe/GitHub-style), and `deliver()` sends the timestamp as its own `X-TestForge-Timestamp` header alongside `X-TestForge-Signature`. A receiver that also checks "is this timestamp recent" can reject a replayed `(body, signature)` pair even though it still verifies cryptographically. If you add a second outbound-signing feature, sign `${timestamp}.${body}` from the start rather than body-only — retrofitting it later is a breaking change for every existing receiver's verification code.
- **Distinguishing network failure causes in a log** (`lib/webhook-dispatcher.ts`'s `formatDeliveryError`) — `fetch` (undici)'s thrown error is always the generic `TypeError: fetch failed`; the actual reason (DNS failure vs. connection refused vs. anything else) lives one level down in `err.cause`, which is easy to silently discard by logging `err.message` alone. Extracted into its own exported function specifically so it can be unit-tested against *synthetic* errors shaped like Node's real ones (`{cause: {code: 'ENOTFOUND', message: '...'}}`) rather than depending on a real DNS lookup's timing inside a test — a live `.invalid`-TLD lookup was tried first and proved too slow/inconsistent across environments to be a reliable regression test on its own (see `webhook-dispatcher.test.ts`). If a future feature needs to log/branch on a specific network failure cause, extract the formatting into a pure function the same way rather than asserting against a real, environment-dependent failure.
- **`npx tsc --noEmit` (bare, no `-p`) is NOT a reliable stand-in for the client's real build.** `client/tsconfig.json` uses TypeScript project references (`"files": []` + `references`), so a bare invocation checks effectively nothing — `noUnusedLocals`/`noUnusedParameters` and the full real scope only get enforced under `tsc -b` (`npm run build -w client`). This was caught only by actually running the CI workflow's steps locally before treating it as done, not by an earlier bare-`tsc` check that reported clean. See `client/CLAUDE.md`.
